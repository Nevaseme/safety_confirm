# PlanD：平常時の位置共有と災害時の救助支援 — 統合設計

2026-10-19 全面改訂。原案：[plan.txt](../../../plan.txt)。

本書は今後の設計であり、記載した機能がすべて実装済みという意味ではない。位置情報の扱いと次の開発順序は本書を正とし、旧設計・旧ロードマップにある矛盾する記述を置き換える。数値は試作の初期値とする。

## 1. 最終目標と基本方針

**災害で通信網が途絶えても、確認・救助が必要な人と場所を把握し、効率よく巡回できること。さらに、登録寝室・スマホの位置・近距離通信・音響・その他のセンサーを使い、埋もれた人を探す救助活動を補助し、対応結果を共有する。**

中心となる流れ：

**平常時から位置を記録・共有 → 地震発生で閲覧と安否確認を開始 → 最後の位置と安否から確認先を選ぶ → 現場へ移動 → 捜索・救助 → 対応結果を共有**

決定事項：

- 平常時も、本人が有効にした位置取得・保存・メンバー間の共有を続ける。
- 平常時は、他のメンバーの位置をユーザーに見せない。本人は自分の位置と共有状態を確認できる。
- 緊急地震速報、または承認済みメンバー1人の「地震発生」で、対象グループの位置閲覧と安否確認を始める。
- 地震開始時から対象者の安否を「未回答」とし、その地震への回答が届き次第「SOS／無事」に更新する。待ち時間は設けない。
- 本人がスマホを操作しなくても位置を取得・共有する。安否の回答は別に扱う。
- 地震前に受信した位置も使う。地震ごとに位置を白紙に戻さない。
- 「無事」の回答や災害の終了では、平常時の位置記録・共有を止めない。
- 地図と安否登録を主画面とし、設定・自分の建物・住民の登録はハンバーガーメニューに集約する。
- Androidを本体とし、iPhoneのPWAとWindowsは実験用に使う。Android2台を必要とする試験は開発の待ち条件にしない。

## 2. 利用の流れ

### 初回準備

1. グループへ参加し、メンバーと端末を承認する。
2. 自分、同居人、建物・住戸・寝室を登録する。建物の「母屋」「離れ」等の分類は任意。
3. 「位置を記録・共有」を有効にし、位置・通信・通知に必要な設定を行う。
4. アプリが最初の位置を保存し、接続できるメンバーへ送る。受信側も端末内に保存する。
5. 設定には「平常時も共有し、地震発生時にメンバーが閲覧できる」と簡潔に示す。

インストールだけで開始したことにはしない。初回設定後は毎回アプリを開いたり、安否ボタンを押したりしなくても記録・共有が進むことを目指す。

### 平常時

- 自分の端末で最新位置を更新し、通信できる経路でメンバーへ差分を送る。
- 各端末は他のメンバーの位置を保存・中継するが、地図や詳細には表示しない。
- 回線がなくても測位できれば保存する。接続が戻ったら最新情報を送る。
- 共有状態は「記録中」「送信待ち」「停止中」等で示す。送信待ちでも測位まで停止したと見せない。

### 地震発生

- 受信端末は開始記録を保存し、閲覧を開き、安否回答を求める。
- 開始を作成・受信した端末では、その地震への回答がまだ届いていない対象者を直ちに「未回答」と表示する。相手端末への通知到達や経過時間を条件にしない。
- 地図には、その端末がすでに持つ最新位置を直ちに表示する。地震後の新しい測位を待たない。
- 稼働している端末は位置取得の頻度を上げる。回答待ちでも測位・共有を続ける。
- 新しい位置が届けば更新する。「無事／SOS」は位置取得に失敗しても保存・送信する。
- 新しい地震では安否と対応状況を新しく管理する。以前の「無事」「救助完了」は引き継がない。

例：13:59の位置をBが保存した後、Aの電源が切れた。14:00にBが地震開始を受け取った場合、BはAの13:59の位置を表示できる。Aの再起動や、新しい位置の送信を待つ必要はない。

### 終了・取消

- 災害が終了・取消・期限切れになったら、他人の位置閲覧を閉じる。
- 記録・共有を有効にしている端末は平常時の頻度へ戻り、更新を続ける。
- 終了済みの災害履歴を開いても、他人の最新位置を閲覧する抜け道にはしない。
- 開始者・終了者・対応結果は履歴に残す。位置の履歴は作らない。

## 3. 独立して管理する3つの状態

| 管理対象 | 状態 | 切替のきっかけ |
|---|---|---|
| 位置の記録・共有 | 有効／本人停止／権限・実行条件により中断 | 本人の設定、OSの実行状態 |
| 災害と位置の閲覧 | 平常・閲覧不可／災害中・閲覧可能／終了 | 速報、地震ボタン、取消・終了・期限 |
| 安否 | 未回答／無事／SOS | 災害開始と本人の回答 |

この3つを1つの「共有中」フラグにまとめない。

- 「無事」にしても位置の記録・共有は続く。
- 災害終了は閲覧を閉じる操作。位置の記録・共有を停止する操作ではない。
- 「位置の記録・共有を停止」は、本人の新規測位・位置送信と保留中の位置送信を止める。安否入力や他の記録の同期とは分離する。
- 本人停止は地震開始、再受信、再起動で解除しない。本人が再び有効にする。
- すでに相手へ届いた位置は、本人停止だけで消えない。最後に届いた位置として扱う。
- Bluetooth停止・接続相手0台でも、可能な測位・保存は続ける。インターネット経路が使えるなら送る。
- 複数災害が重なった場合は、有効な災害が1つでもある間、そのグループの閲覧を開く。終了済み災害の再送では開かない。

## 4. 位置の取得・保存・共有

### 最新位置は災害から独立させる

人・端末ごとの最新位置を持ち、災害IDを必須にしない。災害画面から必要に応じて参照する。登録住居の座標と測位座標は別のデータにする。

位置には次を記録する。

- グループ、対象者、対象端末、作成元、レコードID、更新番号。
- 取得時刻、緯度・経度、水平精度、取得方法。
- 受信端末が記録する受信時刻。
- 本人端末の測位か、別端末による近距離検知かという観測種別。

新しい位置を自端末へ保存してから送信対象にする。相手は永続保存を完了してからACKを返す。

### 位置を消さない・古く戻さない

- 同じ作成元の更新番号で前後を判断する。中継の到着順や受信時刻で「最新」を決めない。
- 空の位置、測位失敗、通信切断、本人停止で、保存済み座標を上書きしない。
- 同じ地点を新しく測り直した場合は取得時刻を更新する。古いキャッシュを読み直しただけなら元の取得時刻を保つ。
- 本人の最後の位置と、別端末が検知した周辺位置は別々の観測として保持する。
- 端末交換は承認済み端末の切替として扱い、旧端末の遅延データで新端末の位置を上書きしない。
- 新しい災害で、以前の位置を新しく測ったように書き換えない。「地震前・13:59の位置」のように元の時刻を示す。
- 電源断時の最後の送信に依存せず、稼働中の保存・送信で備える。通常のアプリで電源オフ後も新しく測位・送信できるとは扱わない。

### 初期の取得方針

| 場面 | 初期設定 |
|---|---|
| 平常時 | 5分間隔を目安に、省電力寄りで取得を要求 |
| 災害中 | 60秒間隔を目安に、位置精度を重視して取得を要求 |
| 初回開始・災害開始・無事／SOS変更 | 保存済み位置を利用しつつ、新しい位置を即時に要求 |
| 送信 | 新しい位置の保存後。未接続なら保留し、再接続時に送る |

SOSは状態と発信時刻を保存し、位置とは独立して送る。SOS後に新しい位置が得られたら、通常の位置更新として保存・共有する。SOS発信時刻と位置の取得時刻は分けて表示し、SOS時の座標を別枠で固定保存しない。

5分・60秒は要求間隔であり、測位成功・相手への到着間隔ではない。平常時の精度で建物を区別できない場合は「周辺」として扱い、取得頻度・精度・電池消費を実機で調整する。[Android：位置取得と電池消費](https://developer.android.com/develop/sensors-and-location/location/battery)

Androidの保存済み位置は利用できる場合に先に使い、その後で新しい位置を求める。OSのキャッシュは空や古い場合があるため、PlanD自身も位置を永続保存する。[Android：最後の位置の取得](https://developer.android.com/develop/sensors-and-location/location/retrieve-current)

### 保存期間

- 平常時・災害時ともに、対象者・端末ごとの取得時刻付きの最新位置を保持し、移動経路を蓄積しない。災害開始やSOSを理由に位置の別コピーを残さない。
- 最新位置は、新しい位置への置換、明示的な削除、グループ脱退・端末失効まで保持する。地震の切替や時間経過だけで最後の1点を消さない。更新が途絶えた場合も、最後に得た位置と取得時刻を残す。
- 開始・取消・終了の履歴は座標と分離し、試作では30日保持する。
- 削除・失効は座標を含まない管理記録として共有し、受信後は古い中継情報から復活させない。未接続の端末には次の接続で反映する。
- 同期用の高水位番号と失効記録は表示履歴と分けて保持し、画面上の履歴が消えた後も古い開始・位置の再取り込みを防ぐ。

## 5. 閲覧の制御と地震の開始

### 平常時の閲覧制御

平常時に制限するのは、他のメンバーの測位位置・検知位置・そこから導いた現在の所在である。自分の位置、登録住居、建物情報は別に扱う。

- 保存・同期用の処理は位置データを扱える。
- 地図・詳細・検索・通知・共有画像・エクスポートに出す際は、共通の閲覧判定を通す。
- 背景復帰、画面回転、災害終了でも判定をやり直し、表示用の位置データを画面状態から除去する。
- 平常時に「屋外にいる」「この建物付近にいる」といった派生情報だけを表示することも避ける。
- 本人への常時通知では、記録・共有していることと停止操作を示す。

試作で実現するのは、正規アプリの操作経路における閲覧制限である。各端末が位置を保持する方式なので、端末内データの直接解析や改造アプリに対してまで秘匿する仕組みとは区別する。実証段階で保護方式を強化しても、「平常時から各メンバーへ保存する」「本人端末が停止していても災害時に開ける」という要件は維持する。

### 開始条件・範囲

- 承認済みメンバー1人が「地震発生」を押せば開始する。投票や別メンバーの承認待ちは不要。
- 手動開始は選択中のグループを対象にする。他グループの位置は開かない。
- 正規の緊急地震速報は、グループに設定した監視地域と照合して開始する。
- 訓練は「訓練開始」から別の種別・識別子で作り、初期は実験グループを対象にする。
- 加速度の衝撃だけで自動的に全員の位置閲覧を開かない。

開始には、災害ID、グループ、開始方法、開始者の承認済み端末ID、開始時刻、閲覧期限、速報なら配信元のイベント識別子を含める。作成元を検証し、名前やグループ名の自己申告だけでは受け付けない。

### 通知と履歴

- 「山田太郎さんが地震発生を知らせました」のように、誰が始めたかを通知する。
- 開始を受け取った端末が通知・中継する。経路がない相手には到達後に通知する。
- 同じ開始の再送やボタン連打では、通知や災害を増やさない。
- 開始者別に履歴を見られる。取り消しても開始者・取消者・時刻は残す。
- 開始者またはグループ管理者が取消・終了できる。本人が位置の記録・共有を停止する操作とは分ける。
- 同時に作られた災害は、利用者が同じ地震にまとめられる。元の作成者と記録は残す。
- 同じ速報の続報で回答を消したり、閲覧期限を延長したりしない。

閲覧期間の初期値は実災害72時間、訓練1時間。取消・終了が先なら閉じる。延長は開始者または管理者による記録として共有する。期限は受信時から取り直さず、元の開始と延長記録に基づく。古い終了・取消を後着の開始が覆さない。時計が大きくずれた記録は自動的に閲覧を開く根拠にせず、時刻を確認できるようにする。

## 6. 安否・所在・建物を分けて地図に示す

### 安否と端末の状態

| 情報 | 扱い |
|---|---|
| 無事／SOS | その地震への本人の回答。状態と回答時刻を保存する |
| 未回答 | 地震開始時の初期状態。その地震への本人の回答がまだ届いていない。位置が届いていても成立する |
| 位置更新あり | 取得時点の位置が分かる。本人の操作は不要 |
| 位置更新なし | 最後の位置を残す。通信停止の理由までは断定しない |
| 近距離で検知 | 検知端末の周辺に対象がいたという観測 |
| 衝撃検知 | 安否を上書きしない追加の観測 |

安否確認は地震開始時だけ求める。平常時に回答を要求しない。開始直後から「未回答」と表示し、本人が回答した端末では直ちに、他の端末ではその回答を受信した時点で「SOS／無事」に変える。通知が相手に届いたか、本人が読んだか、位置が更新されたかは、安否とは別に扱う。

「未回答」は、その災害について有効な本人の回答をまだ持っていない場合の初期表示とし、タイマーで生成する記録にはしない。開始情報の再送・続報や遅延受信で、すでに保存した同じ災害の回答を未回答へ戻さない。回答が開始情報より先に届いた場合も保持し、開始情報を受信した後にその回答を表示する。新しい災害では改めて未回答から始める。

スマホ携帯を基本の利用条件として、その位置を本人の推定位置に使う。新しい屋外位置は建物内を探す優先度を下げる材料にする。本人の「無事」とは別の根拠として保持し、屋外のSOSは引き続き優先する。

### 人・家・建物の関係

- 人に利用端末を関連付ける。スマホを持たない同居人も登録できる。
- 家のまとまりには複数の建物・住戸・住民を関連付けられる。敷地境界や敷地の塗りつぶしは要求しない。
- 登録住居・寝室は捜索の手掛かり。測位点とは別に保存・表示する。
- 人への救助・確認記録と、建物への被害・対応記録を分ける。
- 建物の対応完了には範囲・未確認箇所・記録者を伴わせる。1人の救助完了から建物全体を完了にしない。

### 地図を開いた直後

- 地図を広く表示し、詳細パネルは閉じる。個人名・家の名前はタップ後に出す。
- 平常時は他人の位置マーカーを出さない。地震中は保存済みの位置を表示する。
- 人は人型マーカー。SOSは赤とSOS記号、無事は緑とチェック、未回答は橙と「?」で区別する。
- 災害中、取得から5分を超えた位置には時計印を添える。SOSは古くなっても赤を保つ。
- 取得精度は選択時に円・範囲で示す。全員分の円や建物との線を常時表示しない。
- 有効な保存位置が一切ない人だけ、登録建物に「位置情報なし○人」を表示する。地震後の測位がないだけなら、地震前の最後の位置を使う。
- 建物の損傷・対応は建物輪郭と家型の記号で示す。人のSOSの赤で建物全体を塗らない。未確認の建物を自動的に危険扱いしない。
- 人と建物の表示が重なる場合は集約し、タップで住民と建物の状況を分けて展開する。

タップ後は名前、安否、位置の取得時刻・精度、登録寝室、関連建物、対応記録を表示する。「保存中→端末に保存」「送信待ち→相手端末が保存」を区別し、ボタンを押した結果をその場に示す。

## 7. 通信構成

### 2つの経路で同じ記録を運ぶ

| 経路 | 用途 |
|---|---|
| インターネット同期 | 平常時、離れたメンバーにも最新位置を届ける |
| Nearby Connections | 近くのメンバーとの圏外交換、自動再接続、持ち運びによる中継 |
| 実験用WSS | Android・iPhone PWA・Windowsで同じ同期規則を検証する |

遠くにいる全員への共有をNearbyだけで実現したとは扱わない。インターネット同期の最小部分を開発の早い段階へ移す。回線がなく全員へ到達できない間も、到達済みの端末には最後の位置が残る。

本番のインターネット経路には、未接続メンバー向けの最新位置・災害イベントを保持する同期サーバーを設ける。サーバーの保存ACKと、各メンバー端末の保存ACKは別に扱う。メンバー端末はサーバーに接続できなくても保存済み情報を使える。

既存のWindows実験サーバーは、引き続き経路の中継だけを行う。端末の代わりに保存ACKを返さず、実験サーバーの保持データが届いただけの結果を端末間中継成功に数えない。

### 接続と中継

- 初回は相手を確認し、端末の鍵・グループの承認情報を登録する。
- 再接続では登録済みの相手であることを検証し、位置を交換する前に認証を完了する。
- 端末名・グループ名の一致だけで自動接続先を信頼しない。Nearbyの接続認証とアプリ上のグループ認証を両方扱う。[Google：接続の管理](https://developers.google.com/nearby/connections/android/manage-connections)
- 平常時にも接続・再接続を行い、位置を保存・中継する。相手0台になっても共有設定は有効のまま。
- 保存済みの最新番号を交換し、差分だけ送る。同一レコードの再受信は再保存せずACKできる。
- 保存に失敗した場合は保存ACKを返さない。再試行は間隔を空け、失敗状態を表示する。
- 位置の送信待ちは対象者ごとの最新値へまとめる。SOS等の安否回答・災害開始・取消・対応記録は位置とは別の記録として扱う。
- 中継時は作成元・更新番号・取得時刻を維持する。経路が変わっても同じ記録として重複排除する。
- グループ切替・脱退・本人停止では旧処理を終了し、遅延コールバックを無視する。
- 閲覧を閉じる終了・取消・失効を先に適用し、その後で画面用データを更新する。

初期のNearby探索は、平常時30秒探索・120秒休止、災害中30秒探索・30秒休止を実験値とする。確立済み接続は維持する。再接続間隔と電池消費は実機試験で決め、Windows模擬試験だけで無線動作を確認済みにしない。

## 8. Androidでの実現方式

### 既存基盤と追加部分

Kotlin、Compose／Material 3、ViewModel／StateFlow、Room＋KSP、Nearby、MapLibreを維持し、最小SDKは24。位置取得にGoogle Play servicesのFused Location Providerを追加する。

今回読み取った既存プロジェクトは1.4.5、targetSdk 37、Roomスキーマ4。共有サービスはconnectedDevice型で、COARSE／FINE位置権限にAPI32までの上限がある。実装着手時に現行コードを再確認したうえで、位置用途の権限とサービスを追加する。

### 平常時から稼働する位置サービス

- 本人が画面上で「位置の記録・共有」を有効にしたとき、location型フォアグラウンドサービスを開始する。
- 画面・ViewModelから所有を分離し、画面消灯、他アプリ、画面回転でも処理を継続する。
- Nearby用の共有サービスと位置サービスは役割・停止条件を分離する。通信サービスの停止で位置保存まで止めない。
- location型に必要な位置権限、FOREGROUND_SERVICE、対応OSでFOREGROUND_SERVICE_LOCATIONを宣言・確認する。
- 本人への通知には「位置を記録・共有中」と停止操作を出す。他人に位置を見せないことと、本人に稼働を知らせないことを混同しない。
- 平常時の常時準備が稼働していれば、地震受信時は閲覧判定と取得頻度を変更する。毎回サービスをゼロから起動する設計にしない。

位置用フォアグラウンドサービスは、適切に開始すれば消灯中も位置アクセスを継続できる。locationとconnectedDeviceそれぞれの実行要件を満たす。[位置権限](https://developer.android.com/develop/sensors-and-location/location/permissions)／[サービスの型](https://developer.android.com/develop/background-work/services/fgs/service-types#location)

### 権限・復旧

- COARSE／FINEを要求し、おおよその位置だけの場合も安否・保存・閲覧は使えるようにする。建物単位の判定には実際の精度を使う。
- 使用中の位置許可で開始済みサービスを継続する経路と、背景から復旧する経路を分けて実装する。
- 後者では必要に応じてACCESS_BACKGROUND_LOCATIONを別段階で要求する。Android 11以降の「常に許可」は設定画面で行う。[背景位置権限](https://developer.android.com/develop/sensors-and-location/location/permissions/background)
- 背景位置権限があっても、背景からサービスを開始できる条件を別に確認する。Android 12以降の開始制限、14以降の位置権限検査を満たす。[背景開始制限](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
- OSによるプロセス終了では、保存済みの有効設定を用い、OSが許す経路で復旧を試みる。再起動後の復旧は初回ロック解除後を初期対象とし、BOOT_COMPLETED・権限・サービス型の条件を実機で確認する。
- 本人による停止・強制停止を自動的に解除しない。再開は本人の操作で行う。稼働不能なのに「記録中」と表示しない。
- アプリが動けない間でも、他の端末がすでに保存した位置は災害時に表示できる。

通常の背景処理だけでは、Android 8以降は位置更新が毎時数回程度に制限される場合がある。WorkManagerや定期タイマーだけで5分・60秒の継続取得を実現する設計にはしない。[背景位置の制限](https://developer.android.com/about/versions/oreo/background-location-limits)

### 緊急地震速報

配信元・利用条件・対象地域・速報ID・続報・取消を確認できる経路を選ぶ。端末標準の緊急速報を、一般アプリが自由に読み取れる前提にしない。[気象庁：緊急地震速報のデータ案内](https://www.data.jma.go.jp/developer/weatherdataguide/appendix/1-3-a.html)

稼働中の受信、消灯中の受信、停止状態からの通知・復旧を分けて検証する。速報連携が未完成でも、地震ボタンで同じ閲覧・安否確認を動かせるようにする。手動開始と同一の地震だと確認できた速報は記録を統合し、回答をリセットしない。

## 9. データと処理の分離

| 部品 | 責務 |
|---|---|
| メンバー管理 | 人・端末・グループ・承認・失効・作成元の検証 |
| 位置取得 | 平常／災害の取得頻度、権限、最後の位置、稼働状態 |
| 位置保存 | 災害から独立した最新位置、取得時刻、受信時刻 |
| 災害管理 | 手動／速報／訓練、受領、取消・終了・延長 |
| 閲覧制御 | グループと災害状態に応じた画面・出力への位置提供 |
| 安否管理 | 災害開始時の未回答表示、災害別の回答と回答時刻、衝撃等の観測 |
| 同期 | 差分、保存後ACK、再送、中継、失効処理 |
| 地図・確認先 | 人・建物・寝室・対応状況を組み合わせる |

Roomに位置・閲覧制御に必要なテーブルを追加し、既存の住居・安否・救助・建物を保持して移行する。端末ID、単調な更新番号、本人停止設定も永続化する。

位置・開始者認証・閲覧状態を扱える新しい通信版を定義する。対応していない旧版へ、測位位置を登録住居に偽装して送らない。接続時の機能対応確認で、新方式の位置共有ができる相手だけへ送る。

データ受信・本人操作・サービスの開始停止は順序を管理して処理する。画面は閲覧制御済みのStateFlowを購読し、保存層を直接読んで他人の座標を表示しない。

PWAも同じ識別子・更新順・閲覧制御・保存後ACKを実装し、IndexedDBに保存する。PWAの位置取得と通信試験は画面表示中を対象とし、Androidの消灯中運転を代用したとは扱わない。

## 10. 実装する順序

### 第1段階：位置の常時保存・共有と、地震時の閲覧

- 最新位置を災害から独立して保存する。
- Androidの位置サービスを追加し、画面から有効化して平常時にも取得する。
- 既存の実験用通信と接続済みNearbyで、非表示のまま保存・中継する。
- 地震ボタンで保存済み位置を開き、終了で閉じる。
- 無事／SOSと位置更新を独立させる。地図と操作結果表示を整える。

完成：平常時にBがAの位置を保存し、Aを切断した後にBで地震を開始すると、Aの最後の位置が表示される。B再起動後も成立し、終了後は他人の位置が隠れる。

### 第2段階：平常時の共有を日常運転にする

- 承認済み相手との自動接続・再接続を追加する。
- 離れたメンバーへ届ける最小限のインターネット同期を追加する。
- 平常時の電池消費、消灯中の継続、OS終了・再起動からの復旧を検証する。
- 各端末への保存状況と未送信を区別して確認できるようにする。

完成：毎回アプリを開かなくても、利用可能な経路で位置が更新・共有される。通信断後も最後の位置が残り、再接続で最新へ追いつく。Nearbyの実機間部分は2台目入手後の試験を別記する。

### 第3段階：速報・未回答・衝撃

- 正規の緊急地震速報を手動開始と共通の処理へつなぐ。
- 地震開始直後の未回答表示と、回答受信によるSOS／無事への更新を扱い、位置更新とは独立して共有する。
- 衝撃の観測を追加し、安否とは別に表示する。
- 開始者・取消者・繰り返しの履歴を整える。

完成：本人が操作しなくても位置は更新され、未回答の理由と混同しない。速報・手動開始・取消の重複でも、二重通知や終了後の閲覧再開が起きない。

### 第4段階：PLATEAU・建物・寝室

対象地域の建物形状と利用可能な属性を確認し、登録建物へ関連付ける。必要な地図・属性を事前保存する。登録寝室は手入力または簡易図で扱い、建物データに室内間取りが必ずある前提を置かない。属性がない項目は不明とする。

完成：圏外でも、人の最後の位置、関連建物、寝室、個人と建物それぞれの対応を確認できる。

### 第5段階：確認・救助先を選ぶ

SOS、未回答、衝撃、最新位置、建物情報、対応状況を重ね、確認すべき人と家を絞る。新しい屋外位置を建物内捜索の優先度に反映する。建物の内外を分けられない精度なら周辺の候補を示す。

完成：対象と理由を理解して確認先を選べる。訓練で見落とし・重複対応・対象選定時間を測る。自動採点は判断材料の表示と評価の後に追加する。

### 第6段階：実証運用を整える

第2段階の同期を基に、利用者・役割、端末失効、閲覧制御、保存・削除、真正性、配布・更新を整える。建物評価は対象地域の属性と評価手法を検証してから導入する。

完成：限定グループで、回線の切断・復旧、端末交換、訂正、情報の削除まで運用できる。

### 第7段階：確認すべき家を回るルート

現在地と確認対象リストから、徒歩の巡回順と経路を表示する。優先対象、通行止め、確認完了、新しいSOSに応じて再計算する。訪問順は手動変更できるようにする。

背景地図とは別に、道路・歩行経路の計算用データを保存する。現在地が取れなければ出発点を指定できるようにする。

完成：圏外で経路を計算・再表示でき、訓練で移動距離・所要時間・優先対象への到達を評価できる。

### 第8段階：現場での位置特定と拡張

近距離検知・音響・その他センサーで探索範囲を絞る。別端末の検知位置は「この周辺で検知」として扱い、本人端末のGPS座標と混ぜない。既知の配置で距離・方向・階・閉所の推定可能性を実験し、寝室情報と組み合わせる。

完成：どの条件でどの範囲まで絞れるかを実測で示し、捜索・救助の結果を共有できる。iOSネイティブ版、海外の建物データは独立した拡張として進める。

## 11. 検証と成果物

### 必須シナリオ

| 試験 | 期待結果 |
|---|---|
| 平常時にA→Bへ位置を共有 | Bに保存されるが、Bの地図・詳細には出ない |
| A切断後、Bが地震開始 | Bに保存済みの地震前の位置が出る |
| 地震開始直後、相手の回答は未受信 | 相手の通知受領を待たず、その地震への安否を未回答と表示する |
| Aは安否未回答、測位は継続 | 未回答のまま新しい位置が届く |
| 未回答のAからSOS／無事を受信 | 待ち時間を置かず回答を表示する |
| 回答保存後に同じ災害の開始情報を受信・再受信 | 保存済み回答を表示し、未回答へ戻さない |
| Aが無事に変更 | 無事になり、位置更新も続く |
| SOS発信後に新しい位置を受信 | SOSの状態・発信時刻は変えず、位置と取得時刻を更新する。SOS時の座標は別に残さない |
| 災害終了 | 他人の位置閲覧が閉じ、平常時の記録・共有は続く |
| 次の地震開始 | 最新の保存位置は使えるが、前回の無事・救助完了は持ち越さない |
| 再送・遅延・多経路で同じ情報 | 重複しない、巻き戻らない、無限再送しない |
| 保存失敗 | 保存ACKを返さず、復旧後に再送で保存できる |
| B保存→A切断→BからCへ中継 | CはAと直接接続せず、Bが保持した位置を受け取る |
| 本人停止と測位コールバックの競合 | 停止後の本人位置を新規保存・送信しない |
| 取消・期限切れの開始を後から受信 | 閲覧を開かず、元の開始履歴のみ保持する |
| 旧版データから移行 | 住居・安否・救助・建物の既存情報が残る |

Android1台では、画面消灯、他アプリ、画面再作成、権限拒否・取消、位置設定OFF、通知拒否、無線OFF、接続0台、OS停止、再起動を検証する。本人操作が必要な試験は、操作内容と所要時間を先に伝える。

iPhone PWAとWindowsでは、閲覧の開閉、永続保存、再読込、経路限定の中継、訂正・失効を確認する。Androidの背景動作、Nearbyの探索・無線到達・背景での実受信は別の検証として残す。

成果物は更新Android APK、実験PWA、Windows実験環境、移行手順、試験結果。結果を「実機で確認」「実験用経路で確認」「模擬試験のみ」「未確認」に分ける。長時間の継続性は端末・OS・省電力条件とともに記録する。
