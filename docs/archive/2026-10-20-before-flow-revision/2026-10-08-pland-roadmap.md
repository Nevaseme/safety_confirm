## 1. 最終目標

**通信網が途絶えた災害現場で、確認・救助が必要な家とその理由を把握し、効率よく巡回できること。さらに、登録寝室の情報と近距離通信・音響・その他のセンサーを使い、埋もれた人の居場所の特定を支援して救助を補助し、対応結果を共有できること。**

実現する流れ：

**平時の住居・寝室登録 → 緊急地震速報または「地震発生」ボタンで安否確認を開始 → 安否と端末の観測情報を収集 → 保存・中継 → 建物ごとに判断材料を表示 → 対象の家への巡回ルートを表示 → 現場で居場所の特定を支援 → 確認・救助 → 対応結果と訂正を共有**

利用者は住民と現場の確認・救助担当者を想定する。当面は架空の情報を使う訓練用として開発する。

## 3. 開発段階

### 第1段階：災害ごとの情報と、家単位の対応を管理する

- 災害・訓練の単位を作り、その開始・終了と対象地域を扱う。
- 「無事／SOS」の入力を求める開始条件は、対象地域への緊急地震速報の発表と、ユーザーによる「地震発生」ボタンの操作の2つとする。プロトタイプではグループ内の1人が押せば開始し、複数人の同意は要求しない。
- 最初に「地震発生」ボタンから災害の作成・安否入力の案内・開始情報の共有を実装する。受信した相手も同じ災害について回答し、接続していない相手へは次回接続時に開始情報を渡す。緊急地震速報の実配信との連携は第2段階で追加する。
- 平時の住居登録と、その災害での安否・観測・対応記録を分ける。前回の「無事」「救助完了」を次の災害へ持ち越さない。
- 建物・住戸・住民を区別し、複数の住民を同じ家に関連付ける。最初は手動で建物を登録・選択できるようにする。
- 個人の救助完了と、建物の確認・対応状況を別々に記録する。建物の「対応完了」は対象範囲・未確認事項・記録者を伴う明示的な記録とし、一人の救助完了から自動判定しない。
- 建物の状況も地図に表示し、訂正・再確認を履歴として残す。
- 既存データを保持して移行する。新形式に対応しない端末には、共有できない項目があることを表示する。

**完成条件：** 1人の「地震発生」操作で安否確認が始まり、開始情報を受信した相手も同じ災害へ回答できる。同じ家に複数の住民を登録し、個人と建物の対応を混同せずに共有できる。別の訓練を開始しても過去の記録が今回の状況として表示されない。

### 第2段階：緊急地震速報と連携し、応答なし・衝撃を収集する

- 緊急地震速報の発表を配信経路から取得し、対象地域の端末に「無事／SOS」の入力を求める。「地震発生」ボタンと共通の安否確認処理につなげる。
- 同じ速報の続報・再受信で回答を何度も要求したり、回答済みの安否を消したりしない。手動開始と速報が同じ地震だと確認できた場合も、記録を保持して同じ災害に関連付ける。
- 確認要求を受け付けた端末が回答期限を管理し、未回答なら「この確認への応答なし」を保存・共有する。遅れて要求を受信した場合も、受信前の時間だけで即座に応答なしと判定しない。
- 要求を受信していない端末、監視が停止した端末、通信が切れた端末は、応答なしが確定した端末と区別する。
- 後から「無事／SOS」を回答した場合は現在の表示を更新し、以前の未回答記録は履歴に残す。
- 加速度などによる端末の衝撃検知を追加。落下・持ち運びなどの誤検知を記録して調整し、取り消し・訂正を可能にする。
- 衝撃は安否とは別の観測情報として保持する。「SOS」と「衝撃あり」を同時に表示できるようにする。
- 速報の取得経路・利用条件・遅延・訂正や取消・背景での受信を確認する。端末標準の緊急速報をアプリが直接読める前提にはせず、利用できる配信サービスを選定する。模擬速報による試験と実配信との連携確認は区別する。
- 圏外では「地震発生」ボタンと、受信済みの開始情報の中継を利用する。揺れ・衝撃の検知だけでは新たな安否確認を開始せず、端末の観測情報として扱う。

**完成条件：** 緊急地震速報と1人の「地震発生」操作のそれぞれから、安否入力の案内 → 未回答の記録 → 中継 → 遅れて本人が回答、の流れが成立する。続報で回答を失わず、衝撃を重ねて共有しても本人の安否を上書きしない。実配信との連携が未確認の間は、速報対応を完成扱いにしない。

### 第3段階：接続・再接続の操作を減らす

- 利用者が共有を有効にした間、事前に承認した実験グループの相手との接続・再接続を自動化する。新しい相手の承認方法と端末の信頼確認を先に定める。
- 未送信の情報を保持し、相手が現れたら差分を交換する。保存後の受領確認、重複排除、store-and-forwardを継続する。
- 画面消灯、通信断、権限取消、プロセス終了時の状態と復旧手順を明示する。
- 電池消費と探索間隔を測り、共有の停止をいつでも操作できるようにする。

**完成条件：** 模擬端末で離脱・再参加を繰り返しても未送信情報が届き、古い情報に戻らず、終了後の通信が残らない。実無線・長時間の継続性はAndroid追加後に評価する。

### 第4段階：PLATEAUと登録寝室を地図に統合する

- 対象を1地域に絞り、建物形状・建物ID・建築年・構造・階数の収録状況を調べる。取得できない属性は「不明」とする。
- 第1段階の建物と外部の建物IDを関連付ける。対応が曖昧な場合は確認・修正できるようにする。
- 選んだ地域の地図と必要な建物属性を事前保存し、圏外でも同じ情報を参照できるようにする。
- 家を選ぶと、関連する住民、階数、登録寝室、安否・観測・対応履歴を表示する。位置を図示する場合は住民が登録する簡易図を使い、PLATEAUから室内間取りを取得できる前提にしない。
- 建物の脆弱性評価は、まず属性の表示から始める。評価方法と必要データを選び、専門家と妥当性を確認できたものについて、根拠・適用条件・不明項目を添えて評価を表示する。

**完成条件：** 保存した地域で、家を選択して建物情報・登録寝室・対応状況を圏外でも確認できる。属性の欠損や建物の対応付け誤りを修正できる。

### 第5段階：確認・救助する対象を見つけやすくする

- SOS、応答なし、衝撃、未対応、建物属性で地図・一覧を絞り込む。
- 「なぜこの家を確認すべきか」を、観測時刻・情報源・最終受信時刻とともに表示する。
- 登録寝室と現在の所在・在宅確認を区別する。在宅の確認情報がない場合は「不明」とし、登録住所だけで在宅と判定しない。
- 複数の担当者が残した記録や食い違う情報を確認できるようにする。
- 訓練で、対象を見つける時間、見落とし、重複対応、訂正が届くまでの時間を測って改善する。
- 自動的な優先順位の採点は、判断材料の表示と訓練評価の後に扱う。採用する場合は根拠・不確実性を示し、人が判断を変更できるようにする。

**完成条件：** 「未回答・衝撃あり・建物の注意事項あり・未対応」の家を理由付きで抽出し、寝室の確認から対応結果の共有まで訓練で一巡できる。

### 第6段階：インターネット同期と運用基盤を整える

- インターネット経由の同期を追加する。近距離通信と同じ記録ID・訂正履歴を扱い、両方の経路から届いても重複させない。
- 通信網が復旧したら蓄積した記録を同期し、再び切れても端末内保存と中継を継続する。
- 利用者・役割、記録者の真正性、端末紛失時の扱い、情報の閲覧範囲、保存期限・削除を整える。
- 正式な配布・更新、データ移行、障害時の運用手順を用意する。

**完成条件：** 回線の切断・復旧と複数経路の重複受信で記録が壊れず、誰が何を閲覧・記録できるかが定まった限定的な実証運用を行える。

### 第7段階：現在地から確認対象の家を回るルートを表示する

- 第5段階で選んだ「確認すべき家リスト」を目的地とし、救助・確認担当者の現在地からの訪問順と経路を地図に表示する。
- プロトタイプは徒歩・担当者1人を対象に、指定された優先度を守りながら移動距離や所要時間を減らす巡回順を提案する。訪問順の手動変更にも対応する。
- 地域の道路・歩行経路データと経路計算に必要な情報を事前保存し、インターネットがなくても計算・再表示できるようにする。背景地図の保存だけで経路計算できるとは扱わない。
- 確認済みの家、追加されたSOS、現在地の変化、登録された通行止め・危険箇所を反映して残りのルートを再計算する。到達できる経路がない家は明示する。
- 現在地の精度と取得時刻を表示する。位置情報を取得できない場合は出発地点を手動指定できるようにし、通行状況が未確認の経路はその旨を表示する。

**完成条件：** 現在地と複数の確認対象から巡回順・経路が表示され、確認完了や通行止めを反映して圏外でも再計算できる。訓練で移動距離・所要時間と優先対象への到達を評価する。

### 第8段階：位置特定による救助補助と、他地域・iOSへの拡張

- 近距離通信・音響・その他のセンサーを用いて、埋もれた人の居場所の特定を支援する機能を開発する。まず既知の位置で端末の検出、距離・方向などの推定可能性と誤差を検証し、登録寝室と照合して現場で捜索範囲を絞る表示へつなげる。
- 音響・照度・近接などを組み合わせた閉所推定も検証し、位置特定の補助情報として扱う。測定条件・誤判定・電池消費を記録する。
- 推定位置・範囲、観測時刻、誤差、検出不能を表示する。端末の検出位置と人の所在の確認結果を分けて記録し、捜索・救助後の結果も共有する。
- Mac＋Xcodeを用意できたらiOSネイティブ版を検討する。Androidとの実通信や背景制約を個別に検証し、PWA試験の結果をそのまま適用しない。
- PLATEAU以外の建物データを取り込めるようにし、対象国・地域の属性、単位、ライセンス、言語を扱う。

**完成条件：** 救助補助の試作を訓練で評価し、捜索範囲を絞れる条件・誤差・失敗条件を示せる。閉所推定や端末位置を、人の埋没・所在の確定情報として扱わない。他地域・iOSへの対応は、それぞれ独立して完成条件を確認する。

## 4. 全段階で守る情報の区別

| 情報 | 表示・扱い |
|---|---|
| 無事／SOS | 本人の回答。第三者の対応記録で書き換えない |
| 応答なし | 対象の安否確認への未回答。通信切断だけで判定しない |
| 衝撃・閉所の観測 | 端末の観測。負傷や埋没の断定に使わない |
| 登録住居・寝室 | 平時の登録。現在地・在宅・実際の埋没位置とは分ける |
| 個人の救助完了 | 対象者への対応記録。建物全体の完了へ自動変換しない |
| 建物の対応完了 | 明示された対象範囲への対応。未登録者がいないという保証にしない |
| 建物の評価 | データ・評価方法・欠損を表示。実際の倒壊状況とは分ける |
| 巡回ルート | 保存した経路情報と把握できた通行状況に基づく提案。未確認の通行可否を明示する |
| 捜索時の位置推定 | 観測条件・誤差を伴う手掛かり。端末位置と人の所在の確認結果を分ける |

記録には災害の識別、作成元、対象、時刻、訂正関係を持たせる。端末時計の差や同時更新があっても、一方の記録を無言で消さない。保存形式と通信形式を版管理し、既存情報を保持する。

## 5. 進め方と直近の着手範囲

基本の順序は **第1 → 第2 → 第3 → 第4 → 第5 → 第6 → 第7**。第3段階の実機試験待ちでも、第4・第5段階の実装は進める。第8段階の救助補助は最終目標に含め、機材と実現性に応じて検証を進める。iOS・他地域への展開はそれぞれ独立して進める。

次の実装は第1段階のうち、**「災害・訓練の単位」と「1人が地震発生ボタンを押して始める安否確認」**に絞る。緊急地震速報も同じ開始処理に接続できる構成にする。続いて建物・住戸との関連付けと家単位の対応記録、第2段階の速報連携・未回答記録へ進む。開始から終了までの小さな訓練を作り、既存の保存・同期・中継に接続する。

残るUIの利用者確認は「通信開始・停止」と「経路切替」。別枠の短い確認として行い、大局的な開発計画の中心にはしない。オフライン起動・訂正共有・地図・読み上げなどの技術的な確認は継続して記録する。

Android追加後に行う試験：Nearbyによる探索・接続・圏外交換、消灯中の実受信と中継、移動・範囲外からの復帰、長時間と省電力の影響。これらが未確認の間は、圏外での実無線通信を実証済みとは扱わない。

実在の住民情報を扱う実証へ進む前に、第6段階の権限・真正性・個人情報の扱いを整える。自動接続に必要な端末の信頼確認は第3段階で先行して実装する。

## 6. 技術上の確認根拠

- PLATEAUは地域ごとに収録属性が異なるため、対象地域のデータ確認を第4段階の最初に置く。[国土交通省：PLATEAU開発チャート](https://www.mlit.go.jp/plateau/learning/plateau-development-chart/)
- Androidのセンサーには背景実行時の制約があるため、衝撃・揺れの自動収集は実行状態と電池消費を含めて検証する。[Android公式：Sensors overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview)
- 緊急地震速報の取得経路は、即時配信の提供方法と利用条件を確認して選定する。[気象庁：緊急地震速報のデータ案内](https://www.data.jma.go.jp/developer/weatherdataguide/appendix/1-3-a.html)
