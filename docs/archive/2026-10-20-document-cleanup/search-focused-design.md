# PlanD：誰をどの建物で確認するかを決める設計

2026-10-20：この文書は旧案・検討経緯として保存する。現行仕様は[統合設計](../../superpowers/plans/2026-10-19-integrated-design.md)と[実装計画](../../superpowers/plans/2026-10-08-pland-roadmap.md)を参照。平常時から位置を保存・共有し、速報または必要人数の賛同で閲覧を開く。地図の人アイコンはスマホの最後の測位位置にだけ置く。以下の旧方針を現行の実装指示として使用しない。

2026-10-10改定案。従来の住民・端末・建物の設計を更新する。設計段階であり、測位・推定・新画面は未実装。

## 1. 中心となる体験

**地図を見れば、どの家へ向かい、誰を、どの建物や部屋から確認するかが分かる。**

登録情報と観測を並べるだけでなく、アプリが情報を組み合わせて確認先を提案する。推定は使う。判断の根拠は対象を選んだときに短く示す。

プロトタイプでは「登録利用者は普段スマホを携帯している」を基本の利用条件とし、スマホの位置をその人の推定位置として積極的に利用する。端末の置き忘れや共有の例外を中心に画面を設計しない。位置の誤りや利用者の変更は訂正できるようにする。

屋外と推定できる人は、建物内で捜す優先度を下げる。一方、屋外でもSOSを出していれば現地での救助対象にする。「どこで探すか」と「助けを必要としているか」を組み合わせる。

## 2. 基本の構造

| 対象 | 役割 |
|---|---|
| 確認先：山田さん宅 | 複数の建物と住民をまとめ、現場での訪問先にする |
| 建物 | 形状、番号・任意の名前、関連する住民、登録寝室、被害・確認状況を持つ |
| 住民 | 安否、普段使う建物・寝室、今の推定位置、確認・救助記録を持つ |
| スマホ | 登録された人の位置・応答・衝撃などを集め、保存・中継する |

最初の登録は「このスマホを使う人 → 自宅のまとまり → 普段いる建物・寝る場所」の順。母屋・離れ・納屋などの分類は任意とし、建物1・建物2でも使える。集合住宅では建物の下に住戸を置く。

スマホを持たない同居人も登録できる。位置が得られない人には登録寝室や現場確認を利用する。複数の端末から届いても同じ人は重複して数えない。

## 3. 自動で行う整理

### 安否確認が始まるとき

緊急地震速報との連携、または1人の「地震発生」操作で災害単位の安否確認を開始する。

1. 事前に共有を有効にした利用者の端末で、その時点の位置を取得する。
2. 「無事／SOS」の回答を求める。回答を待たず位置の記録を共有する。
3. 回答、位置、衝撃、未回答の記録を、それぞれ取得できた時点で追加共有する。
4. 位置の変化や本人の回答に合わせて、地図と確認対象の並びを更新する。

これにより、SOSを押せない人についても、位置や登録寝室から確認先を提案できる。位置取得に失敗しても回答の保存・送信は止めない。

最初の実装はアプリ表示中と安否操作時の測位から始める。背景での取得は別の検証項目とし、OSに取得を止められた場合は最後に取得した位置を使う。緊急地震速報の実配信連携と、背景測位の実証はそれぞれ別に完成条件を確認する。

### 所在の推定

| 入手できた情報 | アプリの整理 |
|---|---|
| 新しい位置が建物の外側にある | 屋外と推定。建物内の捜索より後に確認する欄へ移す |
| 新しい位置が建物1と対応する | 建物1での確認候補にする |
| 別の建物に対応する位置がある | その建物を確認候補にし、登録住居との関係も保持する |
| 複数建物にまたがる精度の位置がある | 「建物1〜2の周辺」として候補範囲を示す |
| 有効な測位がない | 登録建物・寝室を確認候補にする。「登録寝室」の根拠を添える |
| 現場で本人を確認した | 現場の確認位置と結果を反映する |

家の外にいることと屋外にいることは分ける。自宅から離れた位置が勤務先の建物に重なる場合は「別の建物」とする。

所在地の推定には測位時刻・精度・建物形状を使う。古い観測しかない場合は最後の位置として残し、屋外として後回しにする判断は更新する。鮮度・位置判定の閾値は訓練で調整できる設定として管理し、実装前に具体値と試験ケースを定める。

Nearbyの接続は通信の成立として扱う。GPS等の位置がなくても周辺での捜索に使えるが、接続しただけで相手がどの建物の内外にいるかを確定する処理は設けない。中継者の位置は元の人の位置へ代入しない。

### 確認の順序

1. **SOSの人**：推定位置または登録寝室へ向かう。屋外のSOSもここに含める。
2. **まだ確認できていない人**：建物内と推定される人、所在が分からず登録寝室を確認したい人。衝撃などの追加情報を横に表示する。
3. **屋外と推定できる人**：建物内の捜索より後に回し、安否の回答を待つ・声をかける対象として残す。
4. **無事・対応済みの人**：折りたたんで見られる。新しいSOSや再確認記録があれば上へ戻す。

これは訓練で評価する初期表示順であり、救助優先度の数値採点は導入しない。現場担当者が確認先や訪問順を変更できる。

「屋外」は無事という本人の回答へ書き換えず、独立した短い状態として使う。画面上では屋外の人を移動させることで実用的な絞り込みを実現する。位置だけで未対応SOSを解除しない。

## 4. 5人の家を使った完成イメージ

同じ家に5人が登録されている。以下は表示と推定の動きを説明する仮想データ。

| 人 | 今ある情報 | 画面が案内すること |
|---|---|---|
| 山田一郎 | SOS。位置は建物1付近。登録寝室は2階東側 | 建物1の確認を優先。位置と寝室を同時に見られる |
| 山田春子 | 未回答。位置は建物1と対応 | 建物1で確認する候補にする |
| 山田健太 | 未回答。測位なし。登録寝室は建物2 | 建物2の登録寝室を確認する候補にする |
| 山田太郎 | 回答なし。新しい測位で庭にいると推定 | 屋外1人として下の欄へ。建物内の捜索優先度を下げる |
| 山田花子 | 無事と回答。公園へ避難したと登録 | 無事1人として折りたたむ |

家の見出しは **「山田さん宅／先に確認する人 3人」**。

内訳は **「SOS1・確認待ち2・屋外1・無事1」**。この一覧では一人を一つの行動区分に入れる。屋外でSOSならSOS側へ入れる。安否と位置の詳細値は別々に保持する。

建物1には「SOS1・確認待ち1」、建物2には「確認待ち1／登録寝室」、建物3は住民の候補表示なし。これだけで、まず建物1、次に建物2という行動につながる。建物3の現場確認状況は住民候補の有無と別に保持する。

太郎が屋外からSOSを送れば、屋外欄からSOS欄へ移り、庭の赤い人マーカーを強調する。一郎への救助完了が記録されれば対応済みへ移るが、建物1の春子は確認候補として残る。

## 5. 地図と操作

### 引いた地図：どの家へ行くか

- 家のまとまりを薄い青で示し、「山田さん宅」と短い「SOS1・確認待ち2」を表示する。
- 細かな寝室・全員の名前・精度の円は展開しない。
- 屋外のSOSは個人マーカーとして表示する。登録宅から遠くにいても、そこから辿れる。

### 家を選ぶ：どの建物で誰を確認するか

- 薄い青の範囲の中に建物1・2・3の形状を表示する。
- 建物の上には人の確認対象数を人型アイコン付きで示す。建物の損傷は建物形状・建物アイコン側の別表示にする。
- 人の推定位置は人型マーカーで表示し、小さな測位記号を添える。下部には「山田太郎／屋外・位置から推定」と短く示す。スマホの内部事情を主役にしない。
- 下部パネルは「SOS・確認待ち」「屋外」「無事・対応済み」の順。最初の欄を開き、残りは人数を表示して展開できるようにする。
- 建物の確認状況は同じパネルの下に簡潔に置く。画面の切り替えを強制しない。

### 人を選ぶ：どこを探し、何を記録するか

- 新しい推定位置を強調し、選んだ人だけ精度の範囲を表示する。
- 登録寝室は位置推定とは違う点線の印で示す。位置が取れない場合は「登録寝室」を先に案内する。
- 最新情報の短い表示例は「建物1付近／10:24測位」「登録寝室：2階東側」「衝撃あり」。計測の詳細は展開先へ置く。
- 「本人を確認」「救助・対応を記録」から現場の結果を保存できる。元の回答や観測は履歴として残す。

色の役割は赤＝SOS、青＝選択と家のまとまり、緑＝無事・対応済み。確認待ちは濃い文字と人型の数で示す。建物全体の色を住民のSOSと連動させない。本文は既存の日本語システムフォントと読みやすい文字サイズを継続する。

メイン機能は「地図」「安否登録」。設定、自分と同居人の登録、建物・寝室の登録はハンバーガーメニューにまとめる。

## 6. 同期と位置の更新

- 本人の回答、測位、直接検知、衝撃、現場確認を別の記録として保存する。自動の行動区分はこれらから組み立て直せるようにする。
- 記録には災害ID、対象者・端末、元の取得時刻、作成元、更新順、訂正関係を持たせる。中継で取得時刻を刷新しない。
- SOSを先に保存・送信し、位置は取得でき次第追加する。位置の更新は新しいSOSを作らない。
- 位置の取得失敗では登録寝室を確認候補にする。測位点そのものを住居座標で補完しない。
- 新しい屋外位置で建物内の候補表示を更新する。関連する住民一覧と元の根拠にはいつでも戻れる。
- 住民IDと端末IDを分けて移行し、既存の回答・住居・対応履歴を保持する。新旧の通信形式を版管理する。

## 7. PLATEAUと将来機能への接続

PLATEAUの建物形状は測位を建物と結び付けるために使う。構造・築年などの属性は、確認候補のある建物の特徴として提示する。「どの人を探すか」と「どの建物を注意して調べるか」を同じ画面で読めるようにする。

登録寝室は建物内での確認開始点になる。将来の近距離通信・音響・その他のセンサーは、家→建物→部屋周辺へ捜索範囲を絞る機能として追加する。屋外の人を建物内で探す時間を減らすことも、救助補助の成果として測る。

将来の巡回ルートは登録宅だけでなく、その災害で選ばれた確認先を使う。屋外のSOSや別の建物にいる対象も目的地にできる。人への対応完了で目的地の必要性を更新し、建物の未確認箇所は別に残す。

## 8. 実装の順序と検証

1. 5人の固定データで家・建物・人の画面を作り、建物1→建物2へ確認が進む様子を確認する。
2. 住民・端末の関連付けと位置記録の保存・共有を追加し、既存データを移行する。
3. 安否確認開始時・回答時の測位、屋外・建物付近・登録寝室による候補整理を追加する。最初は表示中の取得と実験データで検証する。
4. Android1台とPWAで位置取得、未回答者の位置共有、保存後の中継、屋外への移動による候補変更を確認する。
5. 背景測位・定期更新・電池消費を個別に検証する。Nearby実機2台の探索・到達範囲の検証は追加端末を用意できてから行う。

完成を判断する主な例：

- 屋外にいると推定できる太郎が、建物内の確認候補から屋外欄へ移る。
- 屋外からSOSが届けば、位置を保ったままSOS欄へ移る。
- 建物1の一郎を救助しても、春子は確認候補として残る。
- 測位がない健太について、建物2の登録寝室へ辿れる。
- 受信・再送・中継で古い位置が新しい位置を上書きせず、人数も重複しない。
- 古くなった屋外推定で対象が隠れ続けず、再確認が必要な状態へ戻る。
- 端末位置から推定した対象と、現場で確認した対象を履歴で区別できる。

訓練では「最初に確認する家・人を選ぶまでの時間」「不要な建物内捜索」「見落とし」「屋外・建物付近の推定誤り」「状態変更が他端末へ届くまでの時間」を測る。
