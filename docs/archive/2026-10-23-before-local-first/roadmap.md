# PlanD：開発全体計画

2026-10-22再設計案。`plan.txt`、`add.txt`、利用者への確認、[外部資料の調査](2026-10-22-research-and-feature-options.md)をもとに、成果物単位で組み直した。今回確認できた事項以外の追加仕様・順序は提案として扱う。各版の詳細設計を確認してから実装する。

## 1. 最終目標

通信網が途絶えた地震災害で、確認・救助が必要な人と場所、その理由を把握し、限られた人員で対応し、結果を共有できるようにする。近距離通信・音響・その他センサーを使い、埋もれた人の居場所を絞り込む救助支援まで目指す。

最初の利用者は町内会・自主防災組織。**最初の実証版は、地震報告→安否・最後の位置の共有→担当決定→対応→結果の共有までを完成させる。**

## 2. 決まっている範囲

- 地図の開始は対象地域の緊急地震速報、または承認済みメンバーの必要人数の報告。必要人数は `min(10, max(2, ceil(N / 3)))`。
- 同じグループの最初の報告の操作時刻から30分以内をまとめる。成立前の本人取消、一度成立した災害の維持、管理者による終了を扱う。終了まで閲覧を継続する。
- 災害ごとの初回安否回答を地図より先に行う。無事／SOS、回答未受信の応答なし、救助記録による救助済みを表示する。SOSには本人のメモを付ける。
- 最後のスマホ位置は取得から3日以内なら地図へ表示する。位置未受信・3日超は位置不明の一覧へ移し、普段の住居・文字入力した寝室を参照する。
- 地震の経過時間は、メンバー報告の場合、最初の報告の操作時刻を起点にする。本人による位置取得・共有の有効化と、災害成立後の他人の位置閲覧を分ける。
- 建物とスマホを別の情報として扱い、建物から登録者の安否・位置を確認できるようにする。建物評価は黄〜橙の半透明表示とし、取得できた属性と根拠を示す。
- 安否地図・住民一覧では無事／救助済みの氏名を隠す。衝撃・閉所マークは個別アイコンと詳細へ表示する。
- 対応はメンバー自身が開始でき、班長・管理者も担当を調整できる。担当欄には本人が設定した活動名をグループ内で表示する。
- 巡回ルートは表示と対象・訪問順の手動変更まで。通行止めとの連動は後続候補。

細かな表示仕様は[確認事項](2026-10-20-decisions.md)を参照。地図・一覧・安否の採用済み部品を使い、各機能を実データにつなぐ際に必要な操作を追加する。

## 3. 引き継ぐ実装

Android 1.5.3、実験PWA 1.4.0、公開Webデモを土台にする。コードの作り直しは目的に含めない。

| 土台 | 使うもの | 今回の目標に向けて追加するもの |
|---|---|---|
| 住民・住居・建物 | 登録、関連付け、Room／IndexedDB保存 | 固定参加者の識別と権限、測位と住居の分離 |
| 地図と操作 | 個別・集約表示、詳細、凡例、安否登録、Webの一覧 | 実測位・新しい災害状態・担当状況との接続 |
| 通信 | Nearby、実験WSS、保存後ACK、差分・再送・中継 | 新しい情報形式と、参加者・作成者の検証 |
| 災害・対応記録 | 1人開始、本人回答、個人・建物の対応、訂正 | 人数成立、管理者終了、本人SOSメモ、担当と進捗 |
| 背景処理 | 接続済みNearbyの共有サービス | 位置取得、復旧、自動接続の検証 |

当初の画面工程1Aは既存成果として引き継ぐ。追加の一覧移植は下記の成果物に含め、画面だけを独立した終了条件のない工程にしない。実測位・人数成立・担当割当はこれから実装する。過去の確認範囲は[実装・試験状況](../../STATUS.md)に記録済み。

## 4. 開発する順序

R1・R2で最初の実証版を作る。R3以降は、その実証で得た結果を踏まえて詳細化する。R5・R6に含む`add.txt`の追加機能は採用候補であり、着手前に範囲を確認する。

| 版 | 完成させる仕事 | 完成を判定する場面 |
|---|---|---|
| **R1：安否と最後の位置が届く** | 手動の地震報告・人数成立、初回回答、実測位、保存・中継、地図・一覧、SOSメモ、既存の救助結果、管理者終了をつなぐ | Androidの位置とSOSをiPhoneに保存し、Android切断後にWindowsへ中継。保存位置・住居・寝室を確認し、救助結果と終了が戻る |
| **R2：誰が対応するか分かる** | 担当者、未対応／対応中／対応済、対応内容・訂正、活動名を共有する | 別々のメンバーが対象を確認し、引受け・担当調整・結果共有を行える。分断中の重複引受けを再接続後に発見・調整できる |
| **R3：日常から情報が蓄積される** | 省電力を考慮した測位、承認済み相手への自動接続・再接続、インターネット同期、緊急地震速報の実配信を接続する | 日常→地震成立→消灯・通信断→復旧を通し、情報の取得・共有・停止状態と電池消費を確認する |
| **R4：建物と観測を判断に使える** | 1地域のPLATEAU等の属性・評価、オフライン保存、実機の衝撃観測を統合する | 属性と方法を示した建物評価、日時付きの衝撃を、安否・寝室と合わせて確認できる。属性不足は不明として扱う |
| **R5：地域の問題と不足を共有する〈候補〉** | 道路閉塞等の通報に、担当・経過・結果を付ける。必要性を確認して活動可能者、緊急度、必要資材の要請を追加する | 場所付きの問題を報告し、担当が対応、必要な支援を依頼し、解決または引継ぎまで共有できる |
| **R6：関係機関へ情報を渡す〈候補〉** | 合意した報告形式での出力、地域集約と未解決案件の明細、必要に応じた外部システム接続を作る | 実証先の受け手が出力を読み、現場情報の再入力を減らせる。訂正・重複・基準時刻・未受信範囲を確認できる |
| **R7：確認対象を巡回する** | 現在地と選んだ対象から徒歩の順序・ルートを表示し、手動で変更できるようにする | 圏外でも対象と訪問順を変更でき、訓練で移動距離・所要時間を評価できる |
| **R8：埋没者の探索を補助する** | 近距離通信・音響等で距離・方向・階・閉所の手がかりを提示する | 既知の配置で探索範囲をどれだけ絞れたか、誤差・検出できない条件を測り、救助記録へつなぐ |

R3の自動接続・実用インターネット同期、R4の評価方法、R8の推定方法はそれぞれ独立して設計する。大きな基盤を一括開発する工程にはしない。

## 5. 次に作るR1

固定の実験参加者で、以下の3つを順に完成させる。各成果物には画面、保存、共有、試験をまとめる。

1. **地震が成立し、回答が残る。** 人の識別・参加者名簿・管理者を用意し、報告・取消・成立・終了、本人回答を保存・同期する。AndroidとWindows模擬端末で操作し、PWAも同じ規則で動作させる。必要人数と分断後の結果が一致することを確認する。
2. **最後の実測位とSOSを別端末で見られる。** Androidで位置を取得して保存・共有し、既存地図と一覧へ接続する。SOSメモ、取得日時・精度、位置不明、住居・寝室への参照を実データで動かす。PWAは受信表示と中継を担う。
3. **相手が切断しても確認・救助結果が残る。** A→B保存→A切断→B→Cの実験経路で検証し、救助結果・訂正・管理者終了を返す。再起動、保存失敗、再送、古い情報、権限不足からの復旧を確認する。

**R1の完了条件**

- 人数条件はN=1、2、3、5、7、10、27、28、100で仕様どおり。分断・再送・逆順受信で同じ有効記録から同じ結果になる。
- 一度成立した災害は後着の取消で閉じず、管理者の終了後は古い成立記録で開かない。
- 取得済み位置は取得時刻から3日以内に限り地図へ表示し、古い位置の再受信で期限が延びない。住居座標は位置取得の代替にしない。
- 本人の回答、SOSメモ、救助結果・訂正、住居・寝室が再起動後も残り、別端末へ届く。
- 旧データを保持した移行ができる。公開デモの架空値を実際の測位・評価に混ぜない。
- Androidの事前保存した地域地図と受信情報をオフラインで開ける。実験通信は準備後にインターネットを切った同一Wi-Fiでも確認する。
- API24と新しいAndroidで主要フローを確認し、実機・実験経路・模擬・未確認を分けた結果を添える。

R1の位置取得・共有は本人が開始し、参加者の操作条件を揃えた実験で確認する。日常の自動復旧・省電力運用はR3で仕上げる。PWAは保存・表示・中継用の実験端末として必要な機能を追加する。

R1の緊急地震速報はテスト入力で開始処理を確認し、実配信はR3で接続する。初回訓練は手動の人数成立を使う。少人数の試験ではWindows模擬参加者を用い、最低2人の規則を維持する。

## 6. R2で最初の実証版を完成させる

安否と対応状態を分ける。例えば「SOS／対応中／担当：東班」のように、助けが必要な状態と動いている担当を同時に確認する。

- 対応記録は災害と対象者に関連付け、担当・活動名・進捗・対応内容・時刻・記録者を保存する。
- メンバー自身の対応開始と、班長・管理者による担当調整を実装する。住民の氏名非表示と、担当欄の活動名を分ける。
- 分断中の複数人による引受けは記録を保持して再接続後に調整する。割当の到達と本人の引受けをどう表示するかは、詳細設計で確認する。
- 対応済みと個人の救助済みを関連付ける。引継ぎや確認だけで終わった対応の扱いを実証先と決め、本人SOSの記録は保持する。
- 一覧の「未対応の対象」「自分の担当」等の絞り込みは、実データの操作確認に必要なものから追加する。

**実証の完成条件：** 町内会・自主防災組織役の参加者が、対象の発見→担当の確認→対応→結果・訂正の共有を操作できる。見落とし、二重対応、入力負担、情報到達を観察し、残った課題を次の版へ分ける。

## 7. 追加案の選び方

`add.txt`の全項目を[追加機能の検討](2026-10-22-research-and-feature-options.md)で管理する。担当と対応状況は採用済み。道路等の通報、緊急度、活動可能者、資材、外部出力・組織間集約は、最小構成の候補と確認事項を示す。

R2の訓練に合わせ、実証先の報告様式と受け手を確認する。CSV等の出力候補で必要項目を整理し、相手が使えることを確かめてからR6の接続方式を決める。上位へは地域の概況に加え、必要な支援を判断できる案件明細を渡す構成を推奨する。

全国共通の指揮命令系統や資材管理システムを先に作る案は範囲が大きい。まず地域の担当・結果共有を完成させ、通報や不足情報に同じ仕組みを広げる。

## 8. 早期調査と研究

R1の詳細設計と並行して、次の調査を小さく進める。調査の成果は実装済み機能と分けて記録する。

| 調査 | 最初に得る結果 | 接続先 |
|---|---|---|
| 実証先の運用 | 担当の決め方、対応結果の種類、報告先と様式 | R2・R5・R6 |
| 速報配信 | 対象地域・入手方法・利用条件・費用・テスト方法 | R3 |
| 建物データ | 1地域で取得できる形状・構造・建築年代、欠損、評価候補 | R4 |
| 閉所・埋没者探索 | 手元の機種のセンサー、既知配置での音響・近距離観測の小規模実験 | 成果に応じて閉所表示、R8へ |

閉所推定の精度改善は独立した研究として続け、R4の建物属性・衝撃記録を先に完成させる。iOSネイティブ版と海外建物データ対応も、環境・対象が整った時点で独立して計画する。

## 9. 実装・検証の進め方

- Kotlin／Compose／Room／Nearby／MapLibreと既存同期を継続し、変更するデータの保存・移行・画面・通信を一緒に実装する。
- 作成者・記録ID・時刻・版を保持し、受信は保存完了後にACKを返す。通信経路が変わっても同じ記録を扱う。
- Android1台では測位・保存・通知・権限・背景処理を確認し、iPhone PWAとWindowsでは情報交換・保存後中継・分断を試す。PWAは画面表示中を基本にする。
- Nearbyの実無線・画面消灯中の相手あり通信・到達距離は、追加Androidが得られた時点で行う。未実施でも他の成果物を進め、圏外実証済みとは区別する。
- 各版でAPI24と新しいAndroidの主要操作、文字拡大・読み上げ、再起動・移行を検証する。性能は同じデータ・画角・操作条件で比較する。
- 架空データで開発・訓練を進め、実住民情報を扱う実証の前に参加・共有先・保存削除・端末紛失時の運用を実証先と合意する。

## 10. 工程を終わらせるルール

1. 着手時に、その版の完成条件と必要な試験を固定する。
2. 完成条件を満たしたら、APK・必要なPWA更新・試験結果をそろえて版を閉じる。
3. 追加要望は次の版の候補へ入れる。データ損失、誤った対象への操作、主要操作不能など、その版の利用を妨げる問題は現在の版で直す。
4. UIの見栄えだけの改善や追加端末待ちは、他の機能開発と分けて進める。
5. 進捗は「今作る成果物／確認できたこと／残ること／次」の4点を[進捗資料](../../STATUS.md)へ記録する。

次の実装対象は**R1の「地震が成立し、回答が残る」**。新たな画面候補の制作を開始条件にしない。
