# PlanD：追加機能の検討

2026-10-23更新。`add.txt`の案を検討する資料。採用済みの範囲と候補を分ける。資料中の制度・製品仕様は、その対象組織・製品に適用されるものであり、PlanDへの提案はその内容からの設計上の判断として記載する。

## 利用者と最初の成果

利用者への確認により、最初の実証は町内会・自主防災組織による住民確認・初動対応とする。最初に試す版には安否・位置・中継に加え、SOS／応答なしへの担当者・対応状況・対応結果を含める。

`add.txt`はユーザーリサーチをもとにした機能案。調査対象者の人数、発言原文、発生頻度は本資料では未確認のため、各案を利用者全体の確定要望とは扱わない。

| 進め方 | 利点・負担 | 今回の選択 |
|---|---|---|
| 安否と救助結果を先に完成 | 最小の実装量。誰が対応中かは別手段で調整する | 比較案 |
| 安否に担当・対応状況を加える | 地域での初動を一巡でき、既存の対応記録を生かせる | 利用者が選択 |
| 通報・人員・資材・出力・集計の基本機能を段階的に加える | 共通の担当・対応記録を使い、地域の問題と支援要請を扱える | 2026-10-23に利用者がA1〜A6をすべて採用すると回答 |

## 追加案ごとの扱い

| 追加案 | 最小構成の提案 | 採用状況・判断すること |
|---|---|---|
| 誰がどの人に対応しているか | 災害・対象者に、担当者と未対応／対応中／対応済、対応内容・時刻・記録者を関連付ける | 初回実証に含める。本人の対応開始と班長・管理者の担当調整は確認済み。引継ぎの具体的な操作は詳細設計で確認する |
| A1：道路閉塞などの通報 | 場所・見た時刻・状況・報告者、担当・対応履歴 | 採用済み。種別、訂正、重複通報の扱いを着手前に決める。写真は別候補 |
| A2：緊急度 | 判断する人が理由とともに手動設定する。本人SOSはそのまま残す | 採用済み。分類と変更権限を確認する。自動判定は別候補 |
| A3：誰が動けるか | 本人が参加可能を表明し、更新時刻・担当情報と併せて見る | 採用済み。操作と共有先を確認する。安否回答とは別項目 |
| A4：必要資材 | 対応対象ごとに品名・単位・必要数・手配状況を記録する | 採用済み。要請の基本機能を先に作り、在庫・調達管理は別候補 |
| A5：表形式への出力 | 地域集計と未解決案件の明細を、受け手が開ける表で出す | 採用済み。利用者による出力項目・指定ソフトでの確認で実装完了。町内会・区・市・県、消防・警察・自衛隊等の受け手の確認は実運用前に行う。直接API接続は別候補 |
| A6：地域別の集計 | 地域ごとの件数・基準時刻と、必要な案件の明細を渡す | 採用済み。地域の対応表と重複集計の扱いを確認する |

担当欄は本人が設定した活動名（班名・ニックネームも可）をグループ内に表示することで合意済み。安否地図・住民一覧での無事・救助済みの氏名非表示は維持する。

## 通信を後半にまとめる開発順序

2026-10-23の利用者の指示により、まず端末内で安否・位置・担当・対応結果を保存して使える状態にする。採用した追加機能も端末内の実装を先に行い、端末間の共有を最後に組み合わせる。終了条件と実装順序は[計画書](2026-10-08-pland-roadmap.md)、各機能の範囲は[設計書](2026-10-19-integrated-design.md)に記載する。

| 比較した進め方 | 評価 |
|---|---|
| 端末内の操作・保存を完成させ、既存通信へ接続 | 今回の方針。Android1台で機能を順に確認できる。記録形式と更新・訂正の規則は各機能と一緒に整える |
| 画面だけ先に作り、保存・通信をまとめて追加 | 操作の見た目は早く揃うが、再起動や実データの扱いが後半まで確認できない |
| 機能を追加するたびに複数端末で実験 | 共有の問題を早く発見できる一方、端末操作の依頼が頻繁になり、今回の希望に合わない |

[Android公式のオフライン設計](https://developer.android.com/topic/architecture/data-layer/offline-first)は、端末内のデータを画面の参照元とし、通信結果をその保存先へ反映する構成を示している。PlanDでは既存のRoomと同期処理をこの形で拡張し、保存・更新規則の自動試験を先に進める。

今回の採用範囲はA1〜A6の基本機能。通報・対応履歴は神戸市、報告の再利用は消防庁とデジタル庁の資料を参考にし、担当・緊急度・活動可能・資材の情報を対象案件に関連付ける。項目の分類と変更権限は利用者に確認する。組織間の出力は、EEIの項目と実証先の様式を照合する。

直接API接続、在庫・調達管理、自動の緊急度判定、写真付き通報、通行止め連動は未採用の候補として、計画書・設計書の両方に記載した。候補の採用判断と、採用後の実装終了条件を分けて管理する。

この更新ではAndroid、消防庁、Esri、神戸市、デジタル庁、内閣府のISUT・EEI・個人情報指針、INSARAG、気象庁、PLATEAU、Nearbyの主要資料を再確認した。

## 実証で確かめること

同じ訓練シナリオで、確認対象の見落とし、二重対応、担当が分かるまでの時間、訂正の伝達、入力負担を観察する。地域の担当者に実際の報告様式を見せてもらい、必要な情報が受け渡せるか確認する。ここで得た結果を採用機能の改善と、残る拡張候補の採否に反映する。
