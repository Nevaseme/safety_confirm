# PlanD：決定した利用フローの実現可能性

2026-10-20。対象：[統合設計](2026-10-19-integrated-design.md)。文書・既存コードの調査結果であり、今回新機能の実装・実機試験はしていない。

## 1. 結論

**利用フローは既存のAndroidアプリを拡張して実現できる。** 建物・人の表示、人数条件による開放、SOSメモ、救助済み、情報の保存・中継は通常の実装課題。建物の強さの推定と閉所推定は、画面の実装と判定の精度検証を分けて進める。

| 要件 | 判定 | 実現方法・残る確認 |
|---|---|---|
| 必要人数で地図を開く | 実装可能 | 承認済み名簿と人単位の署名付き票を共有。人数条件を各端末で検証 |
| 緊急地震速報から開く | 配信連携で可能 | 対象地域・速報ID・続報・取消を扱える正規配信経路を選ぶ。模擬速報から先に共通処理を検証 |
| 無操作でも位置を取得・共有 | 条件付きで可能 | 本人が開始したlocation型サービスで収集。権限、OS停止、省電力条件は実機評価 |
| 電源断後も最後の位置を表示 | 実装可能 | 受信済みの座標と取得時刻をRoomへ保存。元の端末の再起動を待たない |
| 建物を色分けし、選択する | 実装可能 | MapLibreの建物面レイヤー・属性による色分け・タップ判定 |
| 建物の強さを表示する | データと評価手法に依存 | PLATEAU等の属性と評価結果を別管理。データ不足は不明、UI試作は架空の評価値 |
| スマホの状態・観測マーク | 実装可能 | 安否の本体記号、右上の衝撃、左上の閉所を合成。重なり・文字拡大も検証 |
| 建物から登録者の位置と安否へ移動 | 実装可能 | 建物ID・所有者ID・端末IDで関連付け。現在の在宅判定とは別 |
| SOSメモ・救助済み・表示切替 | 実装可能 | 本人回答と救助記録を別保存し、地図用の状態へまとめる |
| 衝撃の日時を記録 | 検知・共有は可能 | 加速度等で観測。落下・携帯時の誤検知、消灯中の取得漏れを測定 |
| 閉所判定 | 実験が必要 | 照度・近接・動きなどの組合せを比較。「閉所の可能性」の表示・共有を先に実装 |
| 圏外で保存・中継 | 既存基盤を拡張可能 | 保存後ACK・再送・順不同を拡張。Nearby実無線はAndroid追加後に検証 |

## 2. 技術選定の確認

### Context7で確認した範囲

利用者指定のContext7で、公式Android Developers（/websites/developer_android）とMapLibre Native（/maplibre/maplibre-native）を解決し、位置サービス、地図の面描画・属性、背景センサーを照会した。

MapLibreではGeoJSONのローカル読込とスタイル式の資料が得られた。AndroidではWear OS等の周辺資料も混在したため、サービス権限・センサー制限は下記の公式本文で補完した。MapLibreの未確定設計案やiOSの例をAndroidで使用可能なAPIとして採用していない。

### Androidの位置・センサー

位置共有はlocation型フォアグラウンドサービスの用途に合う。型と必要権限を追加し、画面から開始する。背景からの新規開始・復旧には別の制限があるため、「一度開始して継続」と「停止後に再開」を分ける。[Android：サービス型](https://developer.android.com/develop/background-work/services/fgs/service-types#location)

Android 9以降は通常の背景アプリにセンサーイベントの制限があり、画面表示中またはフォアグラウンドサービスで取得する設計が必要。センサーの有無・能力は端末ごとに確認する。[Android：センサー概要](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview)

設計判断：衝撃は観測日時付きの追加情報として保存し、安否と独立させる。閉所は専用APIの呼出しで完成する機能ではなく、日常携帯との識別実験を要する。判定方式を決める前でも、観測の保存・中継・マーク表示は模擬入力で検証できる。

### 地図

MapLibreのFillLayerで建物の面を描ける。タップ地点のqueryRenderedFeaturesを建物レイヤーに絞れば、スマホアイコンとは別に建物を選択できる。[FillLayer](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.style.layers/-fill-layer/index.html)／[queryRenderedFeatures](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.maps/-map-libre-map/query-rendered-features.html)

設計判断：既存のMapLibre＋AndroidViewを継続する。建物はGeoJSON等の専用データ源、スマホは動的な点データ源とし、安否変更で建物の色が変わらない構成にする。建物属性・評価は背景タイルと別に保存する。

### 建物の強さ

PLATEAUには構造・建築年代等と地震動を用い、建物ごとの被害程度を計算・可視化した事例がある。したがって評価結果を地図に載せる方向は実現可能だが、PlanD用の評価方法・対象地域データの適合性はまだ検証していない。[国土交通省：建物振動シミュレーション v3.0](https://www.mlit.go.jp/plateau/use-case/uc25-02/)

既存事例でも、実際の構造部材の配置・物性が3D都市モデルに含まれず、外形や属性から解析パラメータを推定すること、耐震化情報の追加が課題になることが説明されている。「PLATEAUから確定した強度値をそのまま取得する」仕様にはしない。[国土交通省：建物振動シミュレーション](https://www.mlit.go.jp/plateau/use-case/uc23-24/)

設計判断：UIでは「建物の強さ（推定）」とし、結果と根拠を保存する。最初は架空データで画面を作り、実地域では評価法と属性の確認を経て値を供給する。属性が揃わない建物は灰色。構造種別しかないデータから詳細な建材を捏造しない。

### 緊急地震速報

気象庁は速報の発表状況をウェブで案内し、即時提供情報の入手先として気象業務支援センターを案内している。公開された発表履歴の取得だけを速報のリアルタイム受信として扱わない。[気象庁：緊急地震速報のデータ案内](https://www.data.jma.go.jp/developer/weatherdataguide/appendix/1-3-a.html)

設計判断：配信元・利用条件・地域・速報ID・取消の扱いを調べて連携先を選ぶ。OS標準の緊急速報通知を無条件に読み取れるという依存は置かない。実配信の接続がなくても、手動投票と模擬速報で地図・安否・中継を先に完成できる。

## 3. 人数条件とプライバシー

利用者の回答により、必要人数は min(10, max(2, ceil(N / 3)))。全承認済みメンバーを母数に固定し、通信断で必要人数を減らさない。

方式として、①接続人数を母数にする、②全メンバーを母数にして各端末で票を検証する、③サーバーだけで集計する、を比較した。**②を採用する。** ①は接続が少ないだけで開きやすくなり、③は回線断で判定できない。②なら保存・中継で必要票を集められる。

この選択では、分断された端末が必要票を持たない間は地図が開かない。これは設定した人数条件の結果であり、圏外だから自動的に1人へ緩和する動作は加えない。1人の実験グループでも本来の条件を変えず、PWA・Windowsの承認済み実験メンバーで人数を作る。

今回継続する平常時の事前保存方式では、正規アプリの画面を開く条件を強化する。端末内に保持した座標そのものを改造アプリから秘匿するには、別の暗号・鍵配布設計が必要。この差は設計書で明記し、画面の注意書きとして常時並べない。

## 4. 既存実装との差と実装判断

2026-10-20に既存AndroidプロジェクトのManifest、ビルド設定、Resident、CareEventを読んだ。

- 1.4.5、minSdk24、targetSdk37。現在の共有サービスはconnectedDevice型。
- COARSE／FINE権限にはAPI32の上限があり、最新Androidの継続測位用に見直す必要がある。
- Residentの座標は登録住居の座標として扱い、測位レコードを別に追加する。
- CareEventには救助・訂正・メモの土台がある。本人のSOSメモと救助記録は別に拡張する。
- 閲覧人数条件には人ID・端末ID・承認名簿・票が必要。表示名や接続台数だけでは実装しない。

現時点でライブラリを全面変更する必要はない。既存の保存・同期・地図を維持し、位置、投票、観測、建物評価を分けて追加する。Room・通信形式の版を更新し、既存住居を測位へ誤変換しない移行試験を行う。

## 5. 今回確定したことと初期値

確定：最低2人・3分の1・10人上限、スマホの最後の位置だけを地図へ置くこと、建物の色分け、右上の衝撃・左上の閉所、SOSメモ、建物から登録者を参照、救助済みと無事の共通表示切替。

設計上の初期値：投票受付10分、平常5分／災害60秒の測位要求、実災害72時間／訓練1時間の閲覧、SOSメモ500文字、無事表示は初期ON、更新から5分超の古い位置表示。延長も人数条件を通す仕様は今回の目的からの推奨であり、利用者が指定した数値とは区別する。

着手時に選定するもの：速報の配信サービス、実地域とPLATEAUデータ、強度評価の手法、閉所の判定モデル。これらの選定待ちで、第一段階の画面・保存・中継は止めない。

文書確認では、承認済みメンバー1〜1000人について全ての可能な投票数を計算し、人数式が「最低2人かつ3分の1以上、または10人以上」という条件と一致することを確認した。現行文書のローカルリンクと旧方針の残存も確認した。これは設計式・文書の確認であり、アプリの投票実装や実通信の試験結果ではない。
