# PlanD：救助支援の設計

2026-10-24更新。合意済みの利用フローと設計方針をまとめる。実装順序は[開発全体計画](2026-10-08-pland-roadmap.md)、既存機能・確認範囲は[実装・試験状況](../../STATUS.md)を参照。追加機能の採用状況と候補は本書の第9節に明記し、根拠は[検討資料](2026-10-22-research-and-feature-options.md)に分ける。

## 1. 目的と利用の流れ

通信網が途絶えても、確認・救助が必要な人と場所を把握し、効率よく巡回し、対応結果を共有する。寝室情報・近距離通信・音響・その他センサーによる、埋もれた人の居場所特定も支援する。

最初の実証は町内会・自主防災組織による住民確認・初動対応。安否・位置・中継に、対象者への担当と対応状況を加えた版を完成させる。

利用者は、通知を含むアプリに必要なすべての権限を許可することを前提とする。権限が不足している場合は再要求し、確認画面を再表示できない場合は設定画面での許可へ案内する。

1. 自分のスマホ、住居、寝室を登録し、位置の記録・共有を有効にする。
2. 対象地域の緊急地震速報、または必要人数の地震報告で災害が成立する。
3. その災害に未回答なら、地図を開く前に無事／SOSを登録する。回答後に地図で建物の強さとスマホの最後の位置・安否を確認する。
4. SOS／応答なしの人の詳細から、住居・寝室・観測・SOSメモを確認する。
5. 救助した人を救助済みにし、記録・訂正を共有する。
6. 災害終了で他人の位置閲覧を閉じ、平常時の記録・共有へ戻る。

## 2. 地震報告と災害の開始・終了

### 開始条件

正規の配信経路から対象地域の緊急地震速報を受信した場合は、人数待ちなしで開始する。配信元、速報ID、続報・取消、地域を確認する。

手動開始は、全承認済みメンバー数Nに対して **min(10, max(2, ceil(N / 3)))** 人の報告で成立する。最低2人、3分の1を切り上げ、10人に達すれば成立する。未接続者も母数に含む。

| メンバー数 | 必要人数 |
|---|---|
| 1人 | 2人必要なので手動成立不可 |
| 2〜6人 | 2人 |
| 7〜9人 | 3人 |
| 10人 | 4人 |
| 27人 | 9人 |
| 28人以上 | 10人 |

- 同じグループで、最初の報告の操作時刻から30分以内の報告を同じ地震として自動でまとめる。通信分断中の独立した報告も対象とする。
- 集計には押した時刻を使う。遅れて受信しても、この30分以内の報告なら集計対象にする。報告の追加によって時間幅を延長する方式にはしない。
- より早い報告が遅れて届いた場合、未成立の報告は最も早い操作時刻から30分で集計し直す。成立済みの災害は維持する。
- 人単位で集計する。同じ人の連打、複数端末、再送・中継は1人分として扱う。
- 成立前は自分の報告を取り消せる。報告と取消の履歴を残す。本人の報告取消と、管理者による災害終了は別の操作とする。
- 報告者・時刻・現在人数・必要人数を表示し、他のメンバーにも地震報告を通知する。
- 各端末は保存した報告と承認情報を検証し、必要人数が揃った時点で災害の成立を判定する。地図までの表示順は「地図と操作」に従う。通知・共有の到達は利用可能な通信経路による。

### 閲覧の継続と管理者による終了

- 成立した災害は、管理者が終了するまで閲覧を継続する。実災害・訓練とも閲覧期限を設けず、期限切れ・延長機能は実装対象外とする。
- 同じ地震の報告をまとめる30分は集計の時間幅であり、地図の閲覧時間とは別である。
- 一度成立した災害は、後から報告の取消が届いても維持する。分断中に成立より前の時刻で取り消されていた場合も、取消は履歴へ反映する。
- 有効な成立記録を保存・中継し、報告と取消の受信順序が違う端末にも成立状態を共有する。
- 災害全体の終了は管理者だけが行う。終了者・時刻を保存・共有し、受信した端末からその災害に基づく他人の位置閲覧を閉じる。終了後に古い成立記録が届いても、終了状態を維持する。
- 同じ地震の続報・手動報告・再送は既存の回答と救助記録に関連付ける。速報の取消は記録・表示し、成立済み災害の終了は管理者が判断する。
- 訓練は実災害と分ける。実データを使う訓練にも人数条件を適用する。

30分の境界と遅れて届いた報告・取消は、自動試験で検証し、実機間の試験で一致を確認する。端末時計のずれは補正せず、記録された操作時刻を使う。利用者の操作条件に影響する追加ルールは[確認事項](2026-10-20-decisions.md)で合意してから実装する。

## 3. 平常時の位置共有

本人が有効にすると、位置の取得・保存・共有を平常時から続ける。平常時のホームは地震報告と本人の記録・共有状態を表示する。災害成立後は初回の安否登録を経て災害地図を開く。自分の住居登録用の地図は平常時も利用できる。

- 他人の位置は、災害地図・人の詳細・建物詳細・通知に共通の閲覧条件を適用する。
- 無事・救助済み・災害終了後も位置の記録・共有は継続する。
- 本人の停止操作で新規測位と本人位置の送信・保留送信を止める。再開は本人操作による。
- 安否や救助記録の同期は位置取得と別に管理する。共有済みの最後の位置は保持する。
- 試作のプライバシー制御は、端末に事前保存した情報を正規アプリで表示する条件を制御する方式。保存データ自体の暗号学的な秘匿は実証運用段階で別途設計する。

## 4. 保存する情報と表示状態

| 情報 | 単位・内容 |
|---|---|
| 最新位置 | スマホごとの最後の1点、取得時刻、精度、取得方法、更新番号 |
| 安否 | 災害・スマホ単位の本人回答。無事／SOS、回答未受信なら応答なし |
| SOSメモ | 本人のSOSに付ける任意の短文。後から編集可能 |
| 救助記録 | 災害・対象者・記録者・日時・対応内容・訂正履歴 |
| 観測 | スマホ・観測時刻・衝撃／閉所・検知方法と版 |
| 住居・寝室 | 所有者・建物・住戸・寝る階・部屋・場所 |
| 建物評価 | 建物属性・評価方法と版・結果・根拠 |
| 建物への対応 | 災害・建物・確認範囲・未確認箇所・記録者・訂正 |

### 位置

地図には最後に取得したスマホの座標と取得時刻を使う。通信断・電源断・測位失敗でも保存済みの点を表示し、位置を一度も取得・受信していない人は「位置不明」として一覧で確認する。経過時間は測位の取得時刻を基準にし、古い位置の再受信で延長しない。新しい位置は作成元の更新番号で比較する。

位置は災害をまたいで保持し、新しい測位に置き換える。取得時刻と受信時刻、SOSの時刻は別に記録する。位置未取得でもSOS・メモ・救助記録を保存・送信できる。

登録住居・寝室はスマホ位置とは別データ。「位置不明」の人も、安否・住居・寝室を一覧や建物詳細から確認する。最後の位置の保存は継続する。将来の他端末による近距離観測も、本人の測位とは別の記録にする。

### 安否と救助

- 「応答なし」は、その災害への本人回答をまだ受信していない状態。災害成立直後から表示する。
- 安否と位置更新は独立する。位置更新の有無だけで本人の安否回答を変更することはない。
- 新しい災害では安否を確認し直す。位置は最後の点を引き継ぐ。
- 初期は1人1台の主端末を登録する。将来の複数端末も同じ所有者に関連付け、人数集計は人単位とする。
- SOSメモは任意入力で最大500文字。本人のメモと第三者の対応メモを分ける。
- 救助したメンバーが人の詳細から救助済みを登録し、訂正できる。本人回答は記録として保持する。
- 救助済みの後に新たなSOSがあればSOSを優先する。古いSOSの再送とメモ編集は、新しい救助要請と区別する。
- 救助記録には確認した回答版と解決したSOSを関連付ける。並行して届いた未確認のSOSは再対応の対象にする。
- 個人の救助と建物への対応は別に記録する。

### 担当と対応状況

初回実証に含める機能として、SOS／応答なしの対象者への担当と対応状況を共有する。本人の安否回答とは別に、未対応・対応中・対応済、対応内容・時刻・記録者を扱う。

メンバーは自分で対応を開始でき、班長・管理者も担当を調整できる。担当欄には本人が設定した活動名（班名・ニックネームも可）をグループ内で表示する。無事・救助済みの住民氏名を隠す既存表示は維持する。

複数人が引き受けた場合は全員を担当として保持し、班長・管理者が調整する。対応済みは結果の記録を伴う完了であり、本人の救助済みとは別の操作にする。訂正元を記録し、並行した訂正は履歴を残す。安否・人への対応・建物の確認範囲を個別に保持する。

通報種別は自由入力。緊急度は高・中・低・未設定で、班長・管理者が変更する。活動状態は活動可能・対応中・活動不可・未設定。資材は品名・単位・必要数・手配済み数を保存し、不足数は必要数−手配済み数（最小0）とする。通報・資材の訂正は作成者と班長・管理者が行う。

## 5. 地図と操作

### Webで確認する新しい一覧構成（2026-10-22）

公開デモでは、従来画面を左、新しい構成を右に並べて比較する。Android 1.5.3は従来の2タブで、新構成の移植は未着手。

- 下部は「地図／一覧／安否」。一覧はグループ全体を対象に、全員・SOS・応答なし・無事／救助済みを切り替える。
- 「位置不明 ○人」から同じ一覧を位置不明に絞って開く。位置不明の行・詳細は普段の住居と寝室を中心に表示する。
- 吹き出しの人数部分は拡大、下の「一覧」は構成する人の一覧を開く。見出しは「このエリアの○人」で、グループ全体へ戻る入口を設ける。
- 地震の経過時間を上部に表示する。メンバーの報告では、必要人数の成立時刻ではなく、最初の報告の操作時刻から数える。
- 無事・救助済みの氏名非表示を各一覧に適用する。衝撃は提供された中抜きのSVGを使う。

### 共通の画面構成

以下はAndroidへ移植済みの画面構成を含む共通仕様。比較版の確認状況は[実装・試験状況](../../STATUS.md)に記録する。

採用デザインは[公開デモ](https://nevaseme.github.io/safety_confirm/)（`demo/`）。白地、青い操作色、地図／安否の下部タブ、折りたたみ凡例、下から開く詳細をAndroidへ反映する（2026-10-22決定）。

メイン機能は地図と安否登録。設定・グループ・自分の住居／建物登録・地図保存はハンバーガーメニューにまとめる。

その災害への初回回答は、地図の表示前に必須とする。回答済みなら再起動時も地図を開く。下部の「地図／安否」タブで切り替え、「安否」から回答を変更する。地図には大きな安否登録ボタンを常設しない。

### 災害地図を開いたとき

詳細を閉じた地図に、次の2層を表示する。SOS・応答なしの人の氏名はタップ後の詳細に置く。

| 層 | 表示 |
|---|---|
| 建物 | 建物輪郭ごとの強さの推定評価。黄〜橙の半透明の塗り、不明は灰色＋細い斜線 |
| スマホ | 最後の測位位置に無事／SOS／応答なし／救助済みのアイコン |

当面の建物色は、強い側を薄い黄 `#FBE8C5`、中間を明るい橙 `#F2AE5D`、弱い側を濃い橙 `#C5672E` とする。建物の輪郭内に半透明で重ね、弱い建物ほど目立たせる。透明度は採用デモを基準とし、評価の段階数・判定基準は第4段階で選定する。スマホの記号は白い縁で建物の塗りと分離する。

- 拡大時の個別アイコンでは、衝撃マークは右上、閉所マークは左上に表示し、併用できる。
- 安否は色と記号で区別する。拡大時の古い位置には経過時間等を添える。
- 近接・重複するアイコンは、以下の広域表示のルールに従って集約する。
- 「無事を表示」は無事・救助済みに適用する。地図に表示できる位置を持つSOS・応答なしは、この切替に関係なく表示する。
- 「位置不明 2人」のように対象人数を表示し、タップで一覧を開く。
- 地図上の人アイコンは測位座標に置く。敷地の塗り分けは設けない。

広域表示には動的な集約を実装する。

1. 縮小すると、近接するスマホを状態別人数の吹き出しにまとめる。
2. 拡大すると、小さなグループへ段階的に分かれ、最後は個々のスマホアイコンを表示する。
3. 吹き出しをタップすると、そのグループが分かれる縮尺まで拡大する。

広域では1人だけでも吹き出し形式に統一し、各行は安否のアイコンと人数だけを表示する。状態名の別ラベル、位置の経過時間、衝撃・閉所の有無は省き、詳しい情報は拡大時の個別アイコンと人の詳細で確認する。集計元は保存済みの最後のスマホ位置とする。集約方法・表示を切り替える縮尺は着手時に検討する。

### 人を選んだとき

安否・位置の取得時刻と精度を表示する。氏名の公開はSOS／応答なしの人に限定し、無事・救助済みの人の氏名は非公開とする。この条件は人物詳細・建物の登録者一覧・位置不明一覧・記録にも適用する。

SOS／応答なしでは、氏名、SOSメモ、普段の住居・寝室、衝撃日時・閉所の観測、住居の築年数・構造／建材、救助記録を優先する。

住居情報には「普段の住居」、位置情報には「最後のスマホ位置」と明示する。無事・救助済みでは簡潔な詳細と救助記録の訂正を利用できる。

### 建物を選んだとき

建物の属性・評価、登録されている全員の安否と最新位置または「位置不明」を一覧表示する。外出先の登録者も含み、地図に表示できる位置を持つ人を選ぶと、そのスマホの最後の位置へ移動する。地図で無事を非表示にしていても、この一覧では全登録者を確認できる。

建物への対応履歴は詳細に表示する。地図の建物色は強度評価を表す。

保存・接続等の操作には「処理中」「端末に保存」「送信待ち」「相手端末が保存」をその場で短く表示する。画面は操作・凡例・詳細を中心に構成する。

## 6. 建物評価と観測

PLATEAU等の建物形状、建築年／年代、構造、階数を使い、採用する評価手法で建物の強さを推定する。評価方法・版・入力属性・条件を保存する。属性不足は不明として表示し、取得できた粒度で築年数や建材を示す。寝室は利用者が階・部屋・場所を文字入力で登録する。

既存の架空データによる表示を実地域・実センサーへ接続する。背景地図と建物の形状・属性・評価は事前保存し、圏外でも表示する。第4段階の終了には、採用した評価方法の計算結果・建物の色・凡例・根拠表示が一致することまで必要とする。建物属性の表示だけは途中成果として扱う。

衝撃は日時付きの観測として共有する。成立前に起きた衝撃も扱い、保存期間と災害への関連付け範囲は第4段階に向けた測定で決める。閉所は照度・近接・動き等による推定として実験する。検知あり・解除・未判定を区別し、解除時はマークを更新する。

## 7. 実装上の共通方針

- Kotlin／Compose・Material 3／ViewModel・StateFlow／Room・KSP／Nearby Connections／MapLibre、最小SDK24を継続する。
- 測位はFused Location Providerとlocation型サービスを使う。本人が画面から開始し、通知から記録状態を確認できるようにする。
- 位置記録中は平常時5分ごと、災害中1分ごとに取得を要求する。位置記録の開始時・地震成立時・安否変更時にも要求する。この間隔で実装し、実際の取得間隔と電池消費をAndroidで測定する。
- 測位と通信の停止条件を分け、OS・権限・省電力条件ごとの継続範囲を実測する。
- 位置、地震報告・取消・成立・終了、安否、救助、観測を別レコードで保存・同期する。
- 受信側は永続保存後に受領確認を返す。更新番号と記録IDで重複・順不同・再送を処理する。
- 最新位置の送信待ちは最新値へまとめ、操作履歴は保持する。中継時は作成元・取得時刻・更新番号を維持する。
- 旧セッションの遅延処理と現在の処理を分離し、停止・グループ切替を反映する。
- 最初の試験の参加者と管理者は、PCで作った設定ファイルを各端末へ読み込んで揃える。第2段階で端末内の人数・権限を扱い、第6段階で通信相手・作成者の検証へ接続する。本人・報告の検証方式は通信統合の詳細設計で定める。参加者の招待・承認、名簿変更・端末交換は後続の運用整備で扱う。
- Room・通信形式は版管理して移行する。既存の住居・対応記録を保持し、測位を独立して追加する。旧版の1人開始は新版の成立根拠に含めず、相手の対応形式を確認して交換する。
- 実験PWAは画面表示中に同じ保存・中継・閲覧規則を検証する。Windows実験サーバーは非保存の経路中継を担う。

通信は、6A：実験経路の交換・中継、6B：インターネット同期、6C：緊急地震速報の実配信接続、6D：Nearby・自動接続に分けて終了を判定する。6Bと6Cは最終目標に必須。試験用入力と同一Wi-Fiの交換だけで、実配信接続・インターネット同期の完了とは扱わない。

共有試験は、災害の報告・取消・成立・終了、本人の安否・位置・SOSメモ、住居・寝室・建物・住戸の関連付け、個人の救助・担当・対応・訂正、建物への対応・訂正、衝撃、採用した追加機能の元記録を対象とする。建物評価は事前配布データの版と結果を照合し、交換する評価記録があれば中継も確認する。閉所は検知方法の実装後に同じ試験へ加える。

画面は端末内の保存データを参照する。第1〜5段階で操作・保存・再起動・実測位を整え、第6段階で新しい記録を既存通信へ接続する。各段階の自動試験では、他人の記録も独立した試験データから投入し、通常と同じ判定・保存処理を通す。

## 9. 追加機能の採用状況と候補

2026-10-23、担当・対応状況に加え、A1〜A6をすべて基本機能として採用した。以下は実装対象で、実装はこれから行う。終了条件は[計画書の追加機能表](2026-10-08-pland-roadmap.md#5-追加機能案の扱い)にIDごとに記載する。分類・変更権限・出力形式など、表中の確認事項は着手前に決める。

| ID・機能 | 状態 | 設計上の範囲と確認事項 |
|---|---|---|
| A1：道路閉塞等の通報と対応履歴 | 採用済み | 地点・報告者・時刻・状況に担当・対応経過・結果・訂正を関連付ける。住民の安否とは別の対象とし、対象種別と重複通報の扱いを確認する |
| A2：手動の緊急度 | 採用済み | 安否とは別に、判断した人・理由・変更履歴を保存する。分類・変更権限を確認する |
| A3：活動可能な人の表示 | 採用済み | 本人が活動可能の状態を設定し、更新時刻・担当状況とともに表示。状態の種類と共有先を確認する |
| A4：必要資材の要請 | 採用済み | 通報や対応対象に品名・単位・必要数・手配状況を関連付ける。手配を更新する人と状態の種類を確認する |

出力の想定先には、町内会・区・市・県、消防・警察・自衛隊を含める。A5・A6の基本機能は端末内で表を作るところまで実装し、外部機関のシステムへの接続は個別に扱う。

A5は、必須試験に合格し、利用者が出力項目を確認して指定の表計算ソフトで開ければ実装完了とする。実際の受け手による確認は、その組織での実運用前に行う。
