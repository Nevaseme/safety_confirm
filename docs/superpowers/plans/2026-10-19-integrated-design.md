# PlanD：位置・安否・建物を使った救助支援 — 統合設計

2026-10-20改訂。原案：[plan.txt](../../../plan.txt)。[実装計画](2026-10-08-pland-roadmap.md)／[実現可能性と調査根拠](2026-10-20-feasibility.md)。

本書を現在の設計の正とする。将来の機能も含み、実装済みを意味しない。利用者の最新決定により「1人で手動開始」「登録住居をスマホ位置の代用にする」を廃止する。指定されていない時間・頻度・色は試作初期値とする。

## 1. 最終目標と利用の流れ

**通信網が途絶えても、確認・救助が必要な人と場所を把握し、効率よく巡回し、対応結果を共有する。さらに、寝室情報・近距離通信・音響・その他センサーを用いて、埋もれた人の居場所の特定を補助する。**

1. 平常時に住居・寝室・所有者とスマホの関連を登録し、本人が位置の記録・共有を有効にする。
2. 地震が起き、対象地域の緊急地震速報を受信するか、必要人数が「地震発生」を押す。
3. 災害地図を開き、建物の強さの色分けと、スマホの最後の位置・安否を表示する。
4. SOS／応答なしのアイコンから、普段の住居、寝室、SOSメモ、衝撃日時、建物情報を確認する。
5. 確認・救助を行い、救助済みを共有する。必要に応じて訂正・再確認する。
6. 終了すると他人の位置閲覧を閉じる。平常時の位置記録・共有は続ける。

Androidを本体とする。iPhone PWA・Windowsを同期実験に使い、Android2台が必要な試験は開発の待ち条件にしない。

## 2. 地震の成立と閲覧開始

### 自動開始

正規の配信経路から受信した緊急地震速報を、グループの監視地域と照合する。対象となる速報なら投票なしで開始する。配信元・速報ID・続報番号・対象地域を検証し、単なるメンバーの「速報を受信した」という自己申告では開かない。

### 手動開始：利用者が確定した人数条件

承認済みメンバー数を N とする。必要人数は **min(10, max(2, ceil(N / 3)))**。

| メンバー数 | 必要人数 |
|---|---|
| 1人 | 2人必要なため手動では成立しない |
| 2〜6人 | 2人 |
| 7〜9人 | 3人 |
| 10人 | 4人 |
| 27人 | 9人 |
| 28人以上 | 10人 |

- 全承認済みメンバーを母数とし、未接続者も含む。スマホ未所有の登録住民は投票メンバーと区別する。
- 票は人単位。同じ人の連打・複数端末・中継による重複は1票。
- 同じグループ・同じ開始要求への有効な票のみを数える。別の日の地震や訓練の票を混ぜない。
- 通信できる人数が少なくても母数や最低人数を自動で下げない。管理者の単独操作による開始の例外も作らない。
- 最初の人が押した段階では開始要求と1票を保存・共有する。地図を開かず「地震の報告 1／必要人数」と表示する。
- 他のメンバーには報告者と必要人数を通知し、同じ開始要求で「地震発生」を押せるようにする。
- 必要人数の票を保存・検証した端末から地図を開く。圏外では端末ごとの受信時刻が異なり、全員同時の開放は前提にしない。

### 投票の試作仕様

- 版番号付きの承認済みメンバー名簿を使い、開始要求に名簿版・対象グループ・要求ID・作成者・作成時刻・受付期限を固定する。
- 受付期間の初期値は10分。同じ要求への賛同として票を集める。期限切れの要求へは追加投票せず、新しい要求を作る。
- 票は要求ID、名簿版、メンバーID、端末ID、作成時刻、署名を持つ。端末は保存済み名簿と承認済み端末鍵で検証する。
- 名簿が不足・不一致なら補完まで保留し、接続中の人数から母数を推測しない。投票中の人数調整で条件を下げず、変更後の名簿を使う場合は新しい要求にする。
- 名簿の版は管理者が承認した履歴として検証する。開始要求側が勝手に少人数の名簿を作ったり、受信側が知る有効版より古い名簿で新しい要求を開始したりすることは認めない。成立済み記録の検証には当時の名簿を使う。
- 端末の失効記録を受け取ったら、失効時刻以降の票を無効にする。成立根拠が失われた場合は閲覧判定を更新する。分断中は未受信の失効まで即時適用できるとは扱わない。
- 成立記録は根拠となる要求・票を伴う。集計結果の数値だけで閲覧を開かない。元の票が先後どちらで届いても、必要な証拠が揃ってから成立させる。
- 手動開始の閲覧期限は開始要求の作成時刻を基準に固定する。受信や票の追加で延ばさない。受付期限内に作成された有効な票が遅れて揃った場合も、閲覧期間内なら成立を検証できる。大きな時計ずれは自動で採用しない。
- 分断中に別々にできた要求の票は自動合算しない。再接続後、同じ要求への参加を案内する。同一地震の成立済み記録を統合しても、各成立根拠と回答を保持する。
- 未成立要求は作成者が取り消せる。票は送信前に確認して記録し、送信後の票だけの撤回は初期版では設けない。成立後は取消・終了を使う。

### 開始後・終了・履歴

- 開始方法、報告者、賛同者、時刻、取消・終了者を履歴に残す。取消後も誰が操作したか確認できる。
- 同じ要求・票・速報の再送で通知を重複させない。速報の続報で回答を消さない。
- 同一地震の手動開始と速報を関連付ける場合も、安否や救助記録をリセットしない。
- 同一地震でも速報と手動成立の根拠は分けて保持する。速報の取消で無効にするのは速報側の根拠であり、有効な手動成立が残る場合は閲覧を続ける。災害全体の終了操作は別に扱う。
- 閲覧期間の初期値は実災害72時間、訓練1時間。終了・取消はそれより早く閉じる。
- 開始要求の作成者または管理者が取消・終了できる。速報開始では管理者が操作する。
- 延長は新たに同じ人数条件の賛同を得る。1人による繰り返し延長で人数条件を迂回しない。これは今回のプライバシー方針に合わせた設計上の推奨仕様とする。
- 終了・取消・期限切れの開始が再送されても開かない。終了が開始より先に届いた場合も終了を優先する。
- 同じグループで有効な災害が他に残っていれば閲覧は継続する。終了済みの災害履歴から現在位置を閲覧できるようにはしない。
- 訓練は実災害と識別子を分け、実データを使う場合は同じ人数条件とする。模擬速報・架空データの開発画面は実グループの解除経路にしない。

## 3. 平常時の位置共有と閲覧制御

- 本人が有効にした位置の取得・保存・共有は平常時から継続する。他人の位置は正規アプリ上で非表示とする。
- 平常時ホームには地震の報告状況と本人の記録・共有状態を表示する。災害地図は開始条件を満たすまで開かない。自分の位置確認や住居登録用の地図は別に利用できる。
- 閲覧判定は地図・建物詳細・人の詳細・検索・通知・共有画像・エクスポートに共通で適用する。現在の所在を推定した情報にも適用する。
- 画面復帰・回転・終了時も判定し直し、表示用の他人の座標を除去する。
- 「無事」「救助済み」や災害終了では、位置の記録・共有を止めない。
- 本人の「位置の記録・共有を停止」は新規測位・本人位置の送信・保留送信を止める。安否回答と他の記録の同期は別に扱う。
- 本人停止は地震開始や再起動で解除しない。相手に届いた最後の位置は停止操作だけでは消さない。
- 試作では各端末へ事前保存し、正規アプリの閲覧を人数条件で制御する。端末内データを直接解析する相手への暗号学的な秘匿とは区別する。強化時は、元の端末が電源断でも閲覧できる条件を保った鍵管理を別途設計する。

## 4. 位置・安否・救助・観測を独立管理する

| 情報 | 単位・保存規則 |
|---|---|
| 最新位置 | グループ・スマホ単位。災害に依存せず最後の1点を保存 |
| 安否 | 災害・スマホ単位。本人の無事／SOS、回答未受信なら応答なし |
| SOSメモ | 災害・スマホ・本人の回答に関連する短文 |
| 救助記録 | 災害・対象スマホの所有者・記録者。本人の回答と別に保持 |
| 衝撃・閉所の観測 | スマホ・観測時刻・観測方法。災害への関連付けを持つ |
| 住居・寝室 | 所有者・登録住居・建物・住戸・階・場所 |
| 建物の強さ | 建物単位。建築属性・評価方法・結果・根拠・版 |
| 建物への対応 | 災害・建物・確認範囲・記録者。個人の救助と別 |

### 最新位置

- 位置には対象スマホ・所有者・作成元・レコードID・単調な更新番号・取得時刻・緯度経度・精度・取得方法を含める。受信時刻は受信側で別に持つ。
- 同じ作成元の更新番号で新旧を比較する。中継到着順で位置を巻き戻さない。
- 測位失敗、通信断、電源断、本人停止、災害切替で最後の座標を消さない。
- 地震前に受信した位置も、取得時刻を保ったまま直ちに表示する。電源オフ後の新しい測位を前提にしない。
- 平常時5分、災害中60秒を目安に取得を要求する。初回有効化・災害成立・安否変更時も新しい測位を要求する。成功・到着の周期を保証する数値ではない。
- 位置は新しい測位への置換、明示削除、脱退・端末失効まで保持する。移動履歴、災害ごとの座標コピー、固定したSOS地点は作らない。
- 古いキャッシュの再読込では取得時刻を書き換えない。SOS時刻と位置取得時刻は分ける。
- 位置未取得でもSOS・メモ・救助記録を保存・送信できる。
- 別端末による近距離検知は本人の測位と別に保持する。検知した側の座標を本人の正確な位置として代入しない。
- 端末交換・失効を管理し、旧端末の後着情報で新端末の位置を上書きしない。

### 安否と表示状態

画面の名称は利用者指定の「応答なし」に統一する。意味は、その災害への有効な本人の回答をまだ受信していないこと。内部では既存の未回答状態と対応させる。

- 災害成立時から応答なし。待ち時間、通知到達、操作の有無、測位の成功を条件にしない。
- 応答なしでもスマホの位置は更新できる。位置更新が止まっても、無事を自動的に応答なしへ戻さない。
- 回答を開始情報より先に受け取った場合も保存する。開始の再送で既存回答を初期化しない。
- 新しい災害では前回の無事・SOS・救助済みを引き継がない。位置は引き継ぐ。
- 初期は1人1台の主端末を登録する。追加端末の持ち主は共通IDで管理し、安否アイコンは端末単位、投票は人単位とする。スマホ未所有者を家の位置に架空のスマホとして表示しない。

### SOSメモ・救助済み

- SOS時は本人が任意のメモを付け、後から変更できる。初期上限500文字。空欄でもSOSを送れる。
- 本人のSOSメモと第三者の対応メモは書き手を分け、同じ欄を上書きしない。SOS解除後のメモは詳細の履歴に残す。
- SOSの新規発信とメモの編集は識別子・操作種別で区別する。メモの修正だけで救助済みをSOSへ戻さない。
- 救助したメンバーが人の詳細から「救助済みにする」を実行する。記録者・日時・任意メモ・対象の回答版を保存し、訂正・取消を中継する。
- 有効な救助完了があれば救助済みアイコンに変える。元のSOS／応答なしは記録上保持し、本人の無事回答に書き換えない。
- 後から届いた古いSOSは救助済みを覆さない。救助後の新しいSOSは再びSOSを優先し、新しい対応を必要とする。回答版と参照した救助記録で順序を判定し、受信時刻だけで決めない。
- 救助完了には解決したSOSの識別子と確認済みの回答版を記録する。並行した未確認の新しいSOSはその救助完了で覆わず、詳細に再確認が必要と示す。時計の比較だけで救助後のSOSを隠さない。
- 1人の救助済みから建物全員の救助完了を自動作成しない。

## 5. 地図と詳細の画面

### 災害地図の初期表示

詳細パネルは閉じた状態で開く。地図上に名前や敷地の塗りは表示しない。基本の表示は次の2層に絞る。

| 層 | 表示 |
|---|---|
| 建物 | 建物輪郭ごとに強さの推定評価を色分け。不明は灰色 |
| スマホ | 最後の測位位置に無事／SOS／応答なし／救助済みのアイコン |

- スマホは保存済みの測位座標にだけ表示する。更新が古くても最後の位置を残す。住居・寝室へ自動で移動させず、建物輪郭へ吸着させない。
- 座標が一度も得られていない対象は地図に人アイコンを置かず、「位置なし」の一覧や建物詳細から参照できるようにする。
- 衝撃マークはアイコン右上、閉所マークは左上。同時に表示できる。色だけで安否を区別しない。
- 古い位置は輪郭の違いと経過時間で区別し、SOSの意味を薄色で消さない。更新から5分超を古い表示にするのは試作初期値。取得時刻は常に詳細で確認できる。
- 重なるアイコンは件数でまとめ、選択時に各端末を展開する。集約時にもSOS・応答なし・観測ありを見落とさない要約を付ける。
- 「無事を表示」チェックボックスを置き、無事と救助済みの両方に適用する。初期値は表示する。外した場合もSOSと応答なしは残る。絞り込みは表示だけに作用し、位置共有を止めない。
- ハンバーガーメニューへ設定・グループ・自分の建物・住民登録・地図保存を集約。主操作は地図と安否登録。

### スマホのアイコンをタップ

名前、安否、取得時刻・精度を表示する。SOS／応答なしの場合は次を優先して示す。

1. SOSメモと対応状況。
2. 普段住んでいる家、住戸、寝る階・部屋・場所。
3. 衝撃の日時、閉所判定の時刻と観測内容。
4. 登録住居の築年数・建築年・構造／建材・建物の強さの根拠。
5. 救助済みの登録、対応記録・訂正。

「普段の住居」と「最後のスマホ位置」は別に示す。本人の位置が別の建物付近でも、自宅の築年数を現在位置の建物の属性として表示しない。住居へ移動する操作では建物を選択するだけで、人のアイコンを移動しない。

無事・救助済みは簡潔な詳細を基本とし、救助記録の訂正と関連建物への移動は可能にする。

### 建物をタップ

- 建物情報と、そこに登録された人・スマホの安否、最新位置の取得時刻を一覧表示する。
- 登録者が外出先にいても一覧に含める。選ぶとそのスマホの実際の最後の位置へ移動する。位置なしは位置なしと表示する。
- 地図の「無事を表示」を外していても、選択した建物の詳細では関連する全員を確認できるようにする。
- 登録関係を、その建物内での検知や在宅確認として扱わない。
- 建物の確認・対応履歴は詳細内へ置き、地図の強度色と混ぜない。

「保存中」「端末に保存」「送信待ち」「相手端末が保存」を区別し、操作結果をその場に表示する。注意書きを常時並べず、短い凡例と必要な詳細で意味を伝える。

## 6. 建物の強さと観測マーク

### 建物ごとの色分け

建物形状・ID・建築年／年代・構造・階数などをPLATEAU等から取得する。建材が分からず構造種別だけ分かる場合は、取得できた粒度で表示する。築年数は建築年から算出し、年代しか分からない場合は範囲で示す。

- 画面では「建物の強さ（推定）」を短い凡例として表示。薄い色で建物面を塗り、濃いスマホアイコンを前面に置く。
- 評価済みの高・中・低と不明を区別する。具体的な評価式は採用する手法の選定・検証後に確定し、今回の計画だけで木造・築年数の点数を創作しない。
- 最初の画面確認では架空の評価データを使用する。実地域へ切り替える段階で収録属性と既存評価手法を照合する。入力不足は不明とし、安全側の評価に埋めない。
- 評価方法、版、使用属性、評価日時、想定地震動を使う場合はその条件を保存する。実際の被災後損傷と、事前の強度推定は別記録とする。
- 建物の属性・評価・輪郭を対象地域ごとに事前保存し、圏外でも同じ色分けと詳細を表示する。背景地図の保存だけで建物属性も保存されたとは扱わない。
- 室内間取りはPLATEAUから自動取得できる前提にせず、寝室は手入力・簡易図から登録する。

### 衝撃と閉所

- 衝撃は加速度等から検知した端末の観測。日時・強さ・検知方法・版を保存し、安否に重ねる。
- 地震成立前の衝撃も拾えるよう、本人が有効化した平常時の観測と短い事前記録を設ける。災害への関連付け範囲は、成立前10分から終了までを試作初期値とし、履歴には元の時刻を残す。
- 閉所は照度・近接・動き等を組み合わせた推定として開発する。実験段階の名称は「閉所の可能性」。マークなしを「開放空間と確認済み」とは扱わない。
- 観測は検知あり／解除／未判定・未対応を区別し、時刻を持つ。古い衝撃を新しい災害のマークへ自動で持ち越さない。解除後は閉所マークを外す。
- 最初に模擬観測でマーク・同期・詳細を完成させる。実センサーは日常携帯、暗所、覆われた状態等の比較で検知率・誤検知・電池消費を測定してから有効化する。
- 通常のAPIから閉所や埋没が確定的に分かるとはしない。音響を使う追加実験は、マイクの利用状態と実行条件を別に設計する。

## 7. 通信・保存・Android実装

- Kotlin、Compose／Material 3、ViewModel／StateFlow、Room＋KSP、Nearby Connections、MapLibre Native、最小SDK24を継続する。
- Androidの測位はFused Location Provider、継続処理はlocation型フォアグラウンドサービス。本人が画面から有効化し、位置記録中の通知と停止操作を置く。
- 位置サービスとNearby通信の停止条件を分離する。画面終了や接続相手0台だけで測位を止めない。
- COARSE／FINE、location型の権限、背景復旧時の権限・開始制限を扱う。おおよその位置でも保存・安否は利用できるようにする。
- OS停止・再起動からの復旧はOSが許す経路で実装・実測する。常時WakeLockや省電力除外を初期前提にしない。サービスがあるだけで深い休止中の全センサー観測を保証しない。
- 最新位置、開始要求・票・成立根拠、安否・メモ、観測、救助・訂正を別レコードとして同期する。
- 自端末へ永続保存してから送信し、受信側も保存完了後にACKを返す。保存失敗時はACKしない。再送・重複・順不同に対応する。
- 最新位置の保留送信は端末ごとの最新値へまとめる。票・開始終了・救助等のイベントは潰さない。
- インターネットとNearbyは同じID・版・署名を扱う。中継時は作成元・取得時刻・更新番号を維持する。
- 平常時に離れたメンバーへ届けるため、最新位置と必要イベントを保持する最小限のインターネット同期を早期に追加する。サーバー保存と相手端末保存を区別する。
- Windows実験サーバーは引き続き非保存の経路中継のみ。端末の代わりにACKしない。
- 自動接続は承認済み端末に限る。初期の探索周期は平常30秒探索／120秒休止、災害30秒探索／30秒休止として実験し、確立済み接続は維持する。
- グループ切替・脱退・本人停止で旧処理の遅延コールバックを無効化する。削除・失効・終了を適用してから画面状態を更新する。
- 開始・投票・終了の表示履歴は30日を初期値とする。同期の高水位番号、失効・終了の管理記録は別に保持し、古い記録の再受信で復活させない。
- Roomの移行では既存の登録住居・安否・建物・救助を保持する。既存の住居座標を測位位置へコピーしない。
- 新しい通信版と機能対応確認を用意する。旧版の1人開始で新しい閲覧制御を解除せず、旧版へ新形式の位置・投票を偽装して送らない。
- PWAはIndexedDBへの保存後ACKと同じ人数・表示・同期規則を実装する。PWAの位置取得・通信は画面表示中を対象とする。

実コードの2026-10-20確認時点では1.4.5、minSdk24／targetSdk37。位置権限はAPI32まで、共有サービスはconnectedDevice型であり、継続測位用の追加が必要。既存のCareEventには救助・訂正の土台がある。新機能の実装済み・実測済みを意味しない。

## 8. 開発順序と完成条件

詳細は[実装計画](2026-10-08-pland-roadmap.md)へまとめる。

1. **位置・人数条件・災害地図の基本動作**：平常時保存、必要票の検証、最後のスマホ位置、応答なし／無事／SOS、SOSメモ、救助済み、フィルター、建物との相互参照。建物評価と観測は模擬データで画面を先に完成。
2. **日常の共有を継続**：承認済み自動再接続、最小インターネット同期、電池・背景運転・OS停止復旧。
3. **速報と実センサー**：速報配信を接続。衝撃を実測し、閉所推定は独立した実験として並行する。模擬表示と実検知を分ける。
4. **実地域のPLATEAUと強度評価**：属性・輪郭・登録建物の対応、評価手法とデータの検証、オフライン保存。
5. **救助対象の選択を改善**：SOS・応答なし・観測・建物を使った確認先選定を訓練で評価。自動採点より表示の有用性を先に検証。
6. **実証運用**：利用者・役割、認証・失効・データ管理・配布更新を整える。
7. **巡回ルート**：現在地と確認対象から圏外でも徒歩経路・訪問順を表示し、変更できるようにする。
8. **埋没者の位置特定と拡張**：近距離通信・音響等による探索範囲の絞り込み、iOSネイティブ、海外データ。

### 必須試験

| 試験 | 期待結果 |
|---|---|
| 平常時A→B保存、A電源断、必要人数で成立 | Bが地震前の最後の位置を表示。新しいAの測位を待たない |
| N=1、2、3、5、7、10、27、28、100 | 閾値は順に2、2、2、2、3、4、9、10、10。N=1は手動不成立 |
| 閾値未満、同一人物の連打・別端末、未承認票 | 地図を開かない。接続中の人数で閾値を下げない |
| 違う要求・名簿・グループ・期限切れの票 | 合算せず、証拠不足なら開かない |
| 票→成立、成立→票、複数経路・再起動 | 必要証拠が揃えば同じ結果。重複通知・二重開始なし |
| 正規速報、続報、取消、古い開始の後着 | 適切に開閉し、回答をリセットせず終了後に再開しない |
| 応答なしのまま新しい位置を受信 | 位置だけ更新。無事／SOSは自動推定しない |
| 位置更新停止・位置なし・GPS失敗 | 最後の座標と時刻を保持。位置なしを自宅へ代入しない |
| SOSメモ変更と位置更新を別順で受信 | 両方が保持され、古いメモ・位置へ戻らない |
| 救助完了・訂正・古いSOS・新しいSOS | 救助済みを正しく表示し、新しいSOSを隠さない |
| 無事を表示OFF | 無事と救助済みだけ非表示。建物詳細では全登録者を確認可 |
| 衝撃・閉所の同時検知／解除 | 右上・左上を区別し、解除・対象災害を反映 |
| 建物選択、登録者は別の場所 | 登録者の最後の位置へ移動。建物内にいる表示にしない |
| A→B保存、A切断、B→C | CはAに直接接続せずBの保存情報を取得 |
| 保存失敗、終了、権限取消、本人停止 | 誤ACK・位置の再出現・停止後の送信なし |
| 移行・圏外再起動 | 住居と測位を混ぜず、保存位置・地図・建物属性を再表示 |

成果物はAndroid APK、実験PWA、Windows実験環境、移行手順と試験結果。実機・実験経路・模擬・未確認を分ける。Android2台によるNearby実通信、接続相手のある背景中継、長時間の省電力影響は追加端末入手後に確認する。実機操作をお願いする前に、内容と待機時間を伝える。
