## 現在の実装

Androidは1.5.3（versionCode 16、minSdk24、targetSdk37）、実験PWAは1.4.0。Android 16実機へ1.5.3を適用済み。開発先は[android/](../android/)、実験環境は[lab/](../lab/)。

| 実装されているもの | 範囲 |
|---|---|
| 登録・保存 | 住民、住居・寝室、建物・住戸、関連付け、Room／IndexedDB保存 |
| 災害・安否 | 1人による災害・訓練の開始、本人の無事／SOS、終了・履歴 |
| 対応 | 個人の救助・確認、建物の対応範囲、訂正履歴 |
| 地図 | 採用デモをもとにした地図・下部詳細・凡例・位置不明一覧。住居登録用の地図、1地域のオフライン保存 |
| 通信 | Nearbyの手動接続、差分交換、保存後ACK、再送・中継 |
| 背景共有 | 接続済みNearby相手との共有をサービスへ分離 |
| 実験通信 | Android・PWA・WindowsのWSS通信、非保存の経路中継 |
| 操作結果 | 保存・接続状態、再試行、入力保持、設定メニュー |

通常画面は平常時ホームから始まり、災害への初回回答後に地図を開く。安否変更は下部の「安否」で行う。既存の住居座標はスマホの測位点に転用せず、測位未受信者は位置不明の一覧へ置く。

メニューの「画面デモ」（debug版）は独立した架空データを使い、報告人数・初回回答・地図・動的集約・SOSメモ・建物評価・観測・救助済み／訂正の画面を操作できる。通常のRoomや通信には混ぜない。氏名は無事・救助済みの詳細・一覧・記録で隠す。

人数条件・本人確認・新形式の保存同期は1B、実測位は1Cで実装する。通常画面の災害管理は既存の1人開始を使用し、通常データのSOSメモ保存は1Bで追加する。

## 確認済みの範囲

2026-10-22の1.5.3では、デモ建物の形状コピー・再読込を廃止し、元のベクトルタイルへ直接色を重ねる方式に変更。「色・記号の意味」は「凡例」に統一した。デモの色分類は建物IDによる架空の値で、実際の強度評価とは別。JVM50件、API37の描画・凡例試験2件、ビルドが成功。Lintエラー0・警告44。Android 16実機へ更新し、地図・集約アイコン・凡例の表示を確認した。

1.5.3の実機で24回の拡大縮小を2回実行。CPU使用時間は23.80秒・19.80秒、HWUI遅延フレームは両方0.04％。ただし試験終了時の縮尺が想定と異なり、操作前後のカメラ状態を自動確認できていなかったため、1.5.2との差から算出した「約19％減」は参考値に訂正した。今後の改善率は、開始・終了の縮尺と画角を揃えて確認する。記録は `artifacts/android-performance/RESULTS.md` の追記。

PCの空きメモリを確保後（起動前4.8GiB、エミュレーター起動後1.6GiB）、API37をコールド起動して再確認。地図・クラスタ分割・凡例の2試験が成功し、画像に停止通知はなく、クラッシュ・ANRのイベント記録も0件だった。以前のメモリ不足状態で起きた起動待ち失敗・System UI停止は、この再試験では再現していない。ログは `.implementation/android-153-memory-recheck.log` と `android-153-memory-recheck-errors.log`。機能確認であり、実機の速度比較とは別。

`c5eac72`時点の公開Webデモは1画面へ統一し、建物の直接描画、クラスタ更新を縮尺の区切り・移動終了時へ限定、マーカー要素の再利用を実装。PC・390×844のブラウザーで初期表示、詳細、救助・訂正、安否変更、凡例、旧広域リンクを確認。同じ24回の拡大縮小で、クラスタ更新144→48回、GC後のJavaScriptヒープ13.94→8.18MiB（各1回）。ブラウザー全体の使用メモリや長時間利用の測定ではなく、現在の2画面比較版の測定結果でもない。
